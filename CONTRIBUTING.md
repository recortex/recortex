
The local batches cover every test. The four class lists cover `tests/test_scripts.py`. The discovery commands cover the observer, continuity, manuscripts, setup, jobs and dashboard. The four `test_jobs_` patterns split a long run by filename. Keep each batch under five minutes on an idle development machine. Use `mkdir -p .tmp` before running a batch in a fresh clone.

[CI](.github/workflows/tests.yml) runs every test on every pull request and push to `main`, with Python 3.8 on Ubuntu 22.04 and Python 3.14 on Ubuntu 24.04, each in seven shards that run in parallel: `scripts-1`, `scripts-2`, `write`, `versions`, `page`, `jobs-1` and `jobs-2`. A shard is a group of the local batches above; `tests/ci_shards.py` lists them and balances the shards by the commands' measured times (340 to 470 seconds a shard on an idle development machine; split a shard that grows past about ten, because a runner is two to three times slower). A job's limit is 45 minutes. The workflow runs a shard with `python tests/ci_shards.py run NAME`, which runs its commands in order, all of them even after one fails, and exits non-zero if any failed. `python tests/ci_shards.py check` loads the tests without running them and fails if a test that `discover -s tests` finds is in no shard or in two; `tests/test_jobs_ci.py` runs it, and also checks that the shards are the lines of the test block above and that the workflow names every shard, so CI cannot skip a test silently. To add a test, a new `test_*.py` file or a new class in `tests/test_scripts.py` goes into a command of a shard in `tests/ci_shards.py` and into the matching line of the test block above; those tests fail until it does. A new `test_jobs_*.py` file needs neither, because `jobs-1` and `jobs-2` have the four lines that match it by its first letter. The workflow has read-only repository permissions, does not retain checkout credentials, and puts a failing `gh` command ahead of the real CLI during tests so accidental live GitHub calls fail. Its actions are pinned to release commit hashes.

The tests run the scripts against `tests/fake_gh.py`, a local stand-in for `gh` selected with the `RECORTEX_GH` environment variable. They work in temporary folders under `.tmp/` and remove them afterwards; set `RECORTEX_TEST_KEEP=1` to keep them for inspection. The observer's tests that read native transcripts use the system's temporary folder instead, because the observer refuses a transcript below a group-writable folder, which a checkout made with a loose umask is; on macOS `/tmp` is a symlink, which the same checks refuse. No test may contact GitHub.

The suite passes on Python 3.14 on Linux. The lock race test starts its workers with the `fork` start method and is skipped where that method does not exist.

Check the packaging with `claude plugin validate .`.

## Trying the built-in example

```bash
cd examples/octo-repo
S=../../skills/recortex/scripts
export RECORTEX_CONFIG=$PWD/.recortex.json   # the example is not at a project root

python3 $S/setup_labels.py --dry-run
python3 $S/lint_drafts.py --manifest manifest.json
python3 $S/create_issues.py --manifest manifest.json --dry-run
```

The dry run prints the commands issue by issue and makes no network call. In the drafts, issues refer to each other as `NEW-reader`, `NEW-speed` and so on; a real run replaces them with issue numbers. To try a real run, change `repo` in `manifest.json` and `.recortex.json` to a scratch repository of your own, run `setup_labels.py` and `create_issues.py` without `--dry-run`, and set `hub` in `.recortex.json` to the number printed for `NEW-hub`. The run leaves `manifest.json.state.json` beside the manifest, which is what makes a rerun safe; `.gitignore` excludes it.

## The README and the docs

- The README stays under 1,000 words. A section has a picture, a command or a link; a new feature gets one line under "What you get" and its detail goes into `docs/`.
- The five pages in `docs/` are for a person deciding whether and how to use the plugin; each opens with one sentence on what it is for. The pages under `skills/recortex/references/` are written for the session and stay the place for detail.
- The docs and the pictures use the invented record in `docs/pictures/record/`, never a real project and never the built-in example. A test lints that record and builds its page. `docs/pictures/make.sh` remakes the pictures offline through the test fake; it needs Node and Google Chrome and is not run by the tests. Remake them whenever the mind page's look changes.
- A test checks that every relative link and picture resolves.

## Rules for changes

- Scripts use bash, the Python 3 standard library and the `gh` CLI, nothing else.
- A script that writes to GitHub has a `--dry-run` that prints the exact commands. A dry run of `create_issues.py` makes no network call.
- No script deletes issues, comments or labels, or edits a posted comment. The only labels a script changes on an existing issue are section labels that follow its body's headings.
- A new lint rule comes with a test that shows it firing and a test that shows it staying quiet.
- A change to a template's sections is also a change to `KINDS` in `lint_drafts.py`, to `references/issue-model.md` and to the example drafts.
- A link kind, or a change to who may link to what, is a change to `LINK_RULES` in `record_format.py`, to the linter's tests (`test_link_rules_are_exactly_the_table` holds the table as a literal), to the link tables in `references/issue-model.md`, and to its phrases in `PHRASES` of `mind_model.py` (the joins of a passage and the link words of a chain).
- A plain-line label or a fold stem is a change to `record_format.py` (`PLAIN_LABELS`, `WORD_STEM`, `THREAD_STEM`), to the template, to `references/templates.md` and `references/issue-model.md`, and to the examples, and the example memories must still read under `tests/fixtures/compat-0.5.0/` (`CompatTests`).
- `tests/fixtures/hub-1.1.1-manuscript.md` is the hub that the 1.1.1 setup wrote for a manuscript project (`git show a2433a2:skills/recortex/scripts/setup.py`, its `hub_body`), never edited: `OlderHubTests` runs planning, writing and the page on it to show that an older hub needs no hand edit. A change that would need one (a section the hub must hold, a row a command reads) makes `setup.py` do the edit, through `post_verified.py` with `--dry-run`, and updates those tests.
- `tests/fixtures/compat-0.5.0/` is a frozen copy of the 0.5.0 parser and linter, written with `git show 6979c65:skills/recortex/scripts/<name>` and never edited; a test checks its SHA-256 values. A change to the record format that an older reader cannot read turns `CompatTests` red: change the format, not the fixture.
- Marker keys are lowercase letters only (`[a-z]+`): a key with a hyphen or an underscore makes the marker fail to parse on every version, and the comment loses its type and time. The columns of `events` and `FORMAT` in `index.py` stay as they are, since an older version on the same index writes ten values and refuses another format; new tables go into `SCHEMA` as `CREATE TABLE IF NOT EXISTS`, and triggers into `MIND_TRIGGERS`, which only `run_sync` runs.
- A profile's `plan` key (the parts, the headings the plugin may write) is a change to `profiles/*.json`, to `references/profiles.md`, to `KINDS` and the checks of the plan in `lint_drafts.py`, to `plan_rules.py` (the states, which `references/issue-model.md` and `references/planning.md` repeat), to the templates `comment-plan.md`, `comment-text.md` and `comment-proposal.md`, and to the two planner files in `agents/`, whose bodies stay equal below the frontmatter (a test holds that). `examples/octo-repo/` uses the software and research profiles and has no plan draft; the filled examples are in `references/planning.md` and in the tests' paper record (`tests/manuscript_record.py`, `paper()`).
- A topic body is deliverable text: a change to the final-record template or to a profile's section labels keeps the headings in `profiles/*.json`, the label descriptions and `references/profiles.md` in step.
- A GraphQL query uses only fields listed in `tests/fixtures/github-schema-excerpt.graphql`, which is copied from GitHub's public schema. Add the field's signature there, unchanged, when a query needs a new one; `tests/fake_gh.py` rejects anything else, as GitHub would. The reader (`tests/graphql_check.py`) also checks mutations, inline fragments and literal inputs against the `input`, `enum` and `union` definitions of the excerpt, which are copied the same way; `tests/fake_projects.py` answers the Projects and sub-issue operations.
- The resume block is an append-only comment on the hub; no script edits one, and an edited one is never shown. Text printed by the hook stays inside its data frame, includes an issue title only when the issue was opened by an allowed account and never renamed by another, and is printed only for repositories the user trusted.
- The index and the hook state are never written in the project tree, and every entry point (hooks, the session's Bash tool, a user's shell) resolves the same folders: `$XDG_CACHE_HOME` and `$XDG_STATE_HOME`. Do not read `CLAUDE_PLUGIN_DATA`, which Claude Code sets only for hooks. Tests may set `RECORTEX_DATA_HOME` together with `RECORTEX_TESTING=1` to put the index and the state in one sandbox folder (`$RECORTEX_DATA_HOME/recortex`); nothing else uses them. Folders from the environment (`XDG_*`, `RECORTEX_TRUSTED_FILE`) are used only when they are absolute paths. Storage goes through `storage.py`: everything in a `private/` folder with mode 0700 inside the top folder, files written through a temporary file with mode 0600, no symlinks followed, and an index read only when it carries the plugin's mark for this user. A lock of another process is judged and removed only by the process that holds its claim, `sync.lock.claim`, the hard link that only one process can make at a time; the claim gets a new time stamp at once, the lock is read through its path, and that descriptor stays open until the lock is removed; no lock is renamed away. In a project that is set up and trusted, a hook that cannot show the brief says so in one line instead of staying silent. Text from GitHub or from the project reaches a hook payload only inside the data frame and through `brief.defuse()`; outside it, only the plugin's own text, numbers and values checked against a strict pattern.
- A pattern that checks an untrusted name, number or time uses explicit ASCII classes (`[0-9]`, `[A-Za-z0-9]`, not `\d`, `\w` or `\s`) and `fullmatch`, or `re.ASCII` where a class must stay as it is. The scripts write `[0-9]` and never `\d`, in every pattern; a test checks it. A repository name goes through `recortex.valid_repo`, GitHub's form of `owner/name`.
- The agents in `agents/` never post to GitHub and never start another agent. The drafter's and the planners' tools are file tools only. The ask agent has Bash and runs only `index.py query find|recall|timeline|tasks|plan`: the PreToolUse check `pretool_guard.py` (started by `run_pretool_guard.sh` in every project, observer on or off) stops its every other command and, like the rest, fails closed for that agent. The reviewer and the auditor are read-only by instruction: they have Bash for read commands, so do not describe them as unable to write. New hook text is fixed wording plus validated numbers or names, or sits inside the data frame.
- The optional observer, experimental and off by default, is a separate boundary: its settings and approval are private per machine and folder, and the project file can only switch it off. Command hooks persist only bounded native source descriptors and explicit original-user controls, with no model/network calls; a hold is released only from the user's own terminal. Independent sort, draft and review processes have no tools; only the separately approved publisher appends event comments and opens tasks. Mutable bodies, the hub and boards stay with the main session, with these exceptions, all written by code from told memories and never by a model, at the level the user chose and under the worker's lock: a task's list and Result, the hub's `## Active issues` section, the sub-issue links and the board (`observer_jobs.py`), and the status summary: when it is stale and the observer is in automatic mode, its worker writes the In short, has it reviewed by a fresh call, and posts a new resume block through `resume_block.py update`, with the other fields built by code from the index or copied as they were, both calls counted in the middle tier's cap. Use `observer_store.py` for its private durable queue, never the disposable index. Preserve cursor transactions, source identity, payload hashes, uncertain-send reconciliation and visible degraded states. No exactly-once or lossless-transcript guarantee. See [the observer contract](skills/recortex/references/observer.md). Offline tests are in `tests/test_observer_*.py` and `tests/test_jobs_*.py`; runtime feasibility needs separate live evidence and cannot be established by a stub.
- A step is checked only by a mark: `steps` is a kind of memory and `done=` and `dropped=` are marker keys (lowercase letters, like every key), so a change to either is a change to `record_format.py` (`MARKER_KEYS`, `MARK_KEYS`, `MARK_VALUE`, `MARK_RULES`), to the linter's rule, to `lookup.py`, to the index's derive (`DERIVE_VERSION`, the tables `steps` and `marks`), to `task_rules.py` (what a step is, which `references/tasks.md` and `references/issue-model.md` repeat), to `templates/comment-steps.md` and `active-task.md`, to the examples, and `CompatTests` must still read the new comments. A task's list is a copy that `tasks.py render` writes from the told memories under `## Plan` only; a box ticked on GitHub is never believed, a list changed by hand is counted and never overwritten, and a write goes through `post_verified.py` with the live-body check and a backup.
- The observer's levels (Notes only, Assistant, Everything), tiers (sort, middle, strong, each with its own model, runtime check, call cap and token budget) and caps are one table in `observer_runtime.py` (`TIER_OF`, `DEFAULTS`, `LIMITS`) that `references/observer.md`, `references/setup.md`, the setup questions and `observer.py enable` repeat; settings may lower a cap and never raise it, an unknown key is refused, a stopped tier stops only its own jobs, and a folder with no chosen level is paused: no capture, no worker, no model call. A job outside the level is not drafted. Models never act: they label, draft and review; code checks every label, sets the issue of a to-do, a task and a checkpoint, composes `done=`, `dropped=`, `checks=` and `against=` from structured fields when the comment is posted, and writes every rendered copy (a task's list and Result, the hub's active list, the board).
- The plan dialog and the question dialog are sources only in the exact shapes of `observer_sources.DIALOG_SHAPES`, read from the main session's own transcript and matched by call id; a rejected plan's feedback, free text typed into a dialog, the plan file and the plugin's own questions (`OWN_DIALOG`) are never read, and a dialog choice never changes the status of an earlier memory. A new Claude Code wording is a new shape and a new fixture in `tests/fixtures/dialogs/`.
- The manuscript keeper (`keeper_rules.py`, `observer_keeper.py`, `observer_drafts.py`) only proposes: it never runs `write.py apply`, a test fails if its source reaches it, and a draft is written only after the user's recorded "Approve" to that draft's own question, bound to the hashes of the exact files they were shown. None of `write.py check`'s eight refusals is loosened for it.
- Usage is tokens and calls, never money. The observer's calls are exact in its store (also the caps' ledger), a plugin subagent's tokens are read as integers from its own transcript at `SubagentStop`, what hooks inject is an estimate at 4 characters a token, and the main session's own work is not measured. `usage.db` goes through `storage.py`, holds no text, and its writer waits at most 50 ms. The usage and to-do views of the mind page follow the page's rules above and add no tag or attribute.
- `SKILL.md` stays short. Detail goes into `references/`, and every reference file is linked from `SKILL.md`.
- Names live in `names.py`: the plugin's name, the configuration file, the folder, the variable prefix and the workflow, current and from before the rename (`gh-issues-manager`, `.gh-issues-manager.json`, `GHIM_`, `ghim-triage.yml`). Plugin variables are read only through `names.env`, and no other module spells an earlier name, except `run_hook.sh`, which reads the earlier budget name itself; a test scans the tree for them. An earlier name that is still read has a test for the earlier name alone, the current one alone, and both. `renames` in `.claude-plugin/marketplace.json` is append-only history. The `ghim:` markers are the record format and are not renamed. The shared module is `recortex.py`, and the tests also honor `GHIM_TEST_KEEP`.
- The mind page (`mind.py`, `mind_model.py`, `mind_sheet.py`, `mind_text.py`, `mind_versions.py`, `page/mind.css`, `page/mind.js`, `page/icon.txt`): every element goes through `E()`; record text is a text child only, never an attribute value, an element or attribute name, or part of the style or the script; an `href` is `anchor()` or `github_url()`, and no `url` or `image` column of the index is read; the script holds no record text and none of the calls that turn text into markup or reach the network (the page test lists them), and checks every id it reads from the page before a selector or a hash uses it; the style loads nothing. A new element or attribute name goes into `TAGS` or `ATTRS` (an attribute that only some elements may carry goes into `ATTR_RULES` with its values) and into the page test, a math element only through `Page.math()`, the kinds and states of a memory are rows of `KIND_TABLE`, `STATE_TABLE` and `THREAD_TABLE` with one fixed explanation each, and fixed wording of the model goes into `PHRASES` or `FIELD_NAMES`. What the page tells follows `index.memories` and the rules of `references/mind.md`, "Who is told". A request that a button copies into the chat holds only the plugin's own words, a heading that `recortex.HEADING_TEXT` accepts, whole numbers, a time that `CLOCK` accepts and the checked id of a plan comment, never a word of the record (a test plants hostile text in a plan line and in the model's fields and looks at every copied request); it becomes the user's own message.
- The field sheet's labels, sizes and characters live in `field_sheet.py` and move together with `references/fields.md`, the model sheets in `fields/` (a test holds their SHA-256 values), `tests/fixtures/field-sheets/` and the paragraph on field guidance in each of the three agent files. Approved text reaches a payload only through `field_sheet.state`, from the configuration the hook parsed once, and only in its own frame; no hook line outside that frame holds text or a name from a sheet, and `--doctor` prints field names only for an approved sheet. A sheet that breaks the form is refused, never cleaned. No sheet, model or form is loaded from a path a project names. The approvals go through `storage.py`, and the hooks only read them.
- Sub-issue links are computed from the record (`sub_issues.py`: the hub's topics under the hub, each `active` task under the topic its "Destination topic" section names) and never believed from GitHub; a link another parent already holds is reported and left alone, and a GitHub that refuses a link costs one fixed line, never a failed post. The parent of each issue is read in the same GraphQL call as its body edits, and a GitHub that lacks the field is read without it.
- The board (`board_api.py`, `board_rules.py`, `board.py`) is a copy of the record, never part of it. Where a card belongs is one table, `board_rules.place()`, which moves together with `references/board.md` and `BoardRulesTests`; the status names are `board_api.STATUSES`. Everything on the board is untrusted: nothing but item ids, issue numbers, the repository, the plugin's own status names (found by exact option name; any other is "other") and the Why text (compared, never shown) is read, and no text from the board reaches a payload or a terminal line; a test plants hostile text in every field. The `board` entry of the project file is used only in a trusted repository, only for the owner of the record's repository, and only as the user approved it (`board-approvals.json`, through `storage.py`). A project without a board makes no board call and its payloads do not change; a board that cannot be read is one fixed line (`board_api.REASONS`), never a failed sync or post. Hooks never write to GitHub; `board.py apply` is the main session's. A new reason is a change to `REASONS`, to `references/board.md` and to the tests of each reason.
- The branch of versions (`paper_layout.py`, `templates/manubot-front-matter.md`) holds the Manubot-format files and no workflow: nothing is built or run on GitHub, and no script or page reads a build. The layout, the shape of `VERSION.json` (the topics, and the outline the sections were laid out in) and the fixed refusal lines in `versions.py` are part of one contract with `references/versions.md`.
- A stamp a script writes into the record comes from `recortex.stamp` and `recortex.marker_time`, which use the zone the record states (`timezone` in the project file, read by `zones.py`) and UTC when it states none that `zones.py` knows; never from a UTC time formatted by hand. A stamp that is read for order or comparison goes through `record_format.instant`, which takes a marker's offset or a known abbreviation as it is and falls back to the time GitHub gave the comment, never to UTC. `zones.py` is the standard library only (Python 3.8 has no zoneinfo), so a zone it does not know reads as unknown; a change to its table or to what `record_format.to_iso` makes of a stamp raises `DERIVE_VERSION` in `index.py`.
- A new setup question is a row of `QUESTIONS` in `setup_questions.py`, its row in the table of `references/setup.md` ("Questions added after setup"), and a test of each of its states (open, answered, not asked) in `tests/test_setup_questions.py`. The hook counts it from local files and makes no GitHub call, and the prompt hook's reminder (fixed words and a number, at most three times a session, only while `setup.py questions` has not run since the session started, and only when it fits the prompt payload's cap) counts the same way; the answers of a machine are read through `storage.py` and never replaced when they cannot be read; and the `since` of a row decides nothing.
- Shared home folders and changing hosts (1.7.0). An observer approval holds on three bindings, any one of which is enough: the host (`publisher_id`, as before), the key file (`key_file`: an HMAC of the key file's real path and inode, never the device number) and `hosts: "any"` with its `any_host` mark (the user's terminal only). The new fields are keys of the folder's entry in the approvals, never of its `settings`, so 1.5.1 and 1.6.0 judge an entry by the host as they always did; `observer_runtime.approval_reason` gives the first failing code in a fixed order and `approval_valid` is `approval_reason(...) == ""`. A folder above the transcript's project folder that fails only for its owner or its permissions is accepted when the user trusted exactly it (`trusted-ancestors.json`: path, uid, gid, mode and an HMAC under the user key), never the transcript, its project folder or anything inside it, and `_component_problem` and `_read` are not edited (`_problem` wraps the first). The user's own commands are the terminal rows of `observer_hooks.COMMANDS`, held equal to `pretool_guard.USERS_ONLY` (with `--hosts any` and `publish.py`), and the hook refuses a session's call in every project. Two prompt lines have caps of their own (`dashboard_notes.CAP`, `task_reminder.CAP`) and take no room from `brief.CAPS`; a dashboard action writes a note (`dashboard_notes.py`, strict on read) and never fails for it. `publish.py` builds its own page (`mind.public_text`), checks that it is static and holds nothing the privacy rules refuse, asks for a typed confirmation, creates no repository, branch or site and reads the file back. `seed` is a version-one map action for a map with no branch, by a user. The worker's host lease (`observer_lease.py`) is a gate in front of its lock and never replaces it.
- Examples use invented projects only.
