# Hooks, the local index and compile

> Commands on this page write `scripts/<name>` for short. That is the `scripts` folder of this skill, next to `SKILL.md`; call it by its full path.

The plugin keeps every session, resumed or compacted session and subagent aware of the record without anyone asking. Four brief hooks print a short brief; a local index lets them do that in a fraction of a second; `compile.py` turns the record into the finished deliverable and its history. GitHub stays the record throughout: the index is a copy that can be deleted and rebuilt at any time. The optional [observer](observer.md) adds local capture, task context and explicit holds through separate handlers; its pending queue is durable state, not part of this disposable index. This page describes the original brief handlers.

## The four hooks

| Hook event | Prints | Reads GitHub | Size target |
|---|---|---|---|
| `SessionStart` (startup, resume, clear, compact, fork) | The record brief: the rules for writing to the record, the hub, the deliverable topics by section (numbers and titles only), the open `active` issues, the issues that need triage, and the newest allowed resume block; one line on the field guidance when the project has a sheet: that it is shown, or why not, and, when the project is marked as handling sensitive material, the marks in fixed words and that step 7's reviewer must answer the confidentiality question before anything that will be cited is posted | Yes: it syncs the index first, within its time limit, and falls back to the index as it is, saying how old it is | under 6,000 characters; its head also holds one fixed sentence that asks the session to start the part of an answer that uses the record with "From the record:" |
| `SubagentStart` (every agent type) | A short brief for the subagent: where the record is, the issues in play, and the subagent rules (read the record for facts; post only when the task says so; return facts with paths, numbers with denominators and what is not established); with an approved field sheet, its frame between the rules and the data frame ([fields.md](fields.md)) | No | under 3,500 |
| `UserPromptSubmit` | One line: the hub, the active issues, "record events as they happen" | No | under 400 |
| `PreCompact` (manual, auto) | Instructions for the compaction summary: keep the hub and issue numbers in play, every result, decision or failure of the conversation marked posted or not, with enough detail to post it, and the next action; the record is authoritative | No | under 2,000 |

A fifth hook, `SubagentStop` (since 1.5.0), prints nothing and returns no context. When one of the plugin's own subagents stops (`recortex:record-auditor`, `record-drafter`, `record-reviewer`, `record-planner`, `record-planner-session` or `ask`; the matcher is anchored, so another plugin's agent of the same short name does not count), it adds that run's four token counts and its model name to `usage.db`. The path it is given must be this project's own native subagent transcript (the same checks as the observer's sources), and Claude Code has not finished writing that file when the hook fires, so the hook reads it again every 0.1 s for at most 1.5 s until the subagent's last message is there; if it never is, nothing is written. Only whole numbers and a model name leave the transcript. `usage.db`, a small SQLite file in the repository's private state folder (mode 0600, no symlink followed), also holds how many characters each hook added to a session's context, the base of the page's estimate at 4 characters a token; it holds no text, a writer waits at most 50 ms for it and then gives up, rows older than 35 days are removed by the observer's daily cleanup, and `hooks.py --doctor` says when it cannot be written. [observer.md](observer.md) and the mind page's last view ("What did recortex use?") tell what it is for.

No hook can make the skill load, so each payload carries the rules itself and says to invoke the `recortex` skill before writing anything to the record. Claude Code writes any injected text over 10,000 characters to a file and shows only a preview; the payloads stay well below that.

`UserPromptSubmit` prints its line only when the line changed since the last brief of that session, or every tenth prompt. Both are set in `.recortex.json`:

```json
"prompt_hook": {"enabled": true, "every": 10}
```

`python3 scripts/hooks.py --print` shows the four payloads and their sizes, for the user to check. `python3 scripts/hooks.py --doctor` says why the brief is or is not shown: the configuration, the trust status, whether `gh` is found and which github.com account it is signed in as (never as a problem, and the login only when it has GitHub's form), each storage folder with its owner and mode, the index and its age, the last sync failure, the payload sizes and the state of the field guidance (never as a problem, and with field names only for an approved sheet). Of GitHub it asks only which account `gh` is signed in as and, for a project with a board, about the board; it changes nothing and never prints the key.

### The live dashboard's part

At a session start of a configured and trusted project, with at least half a second of the budget left, the hook makes one local connect to the live dashboard server (`dashboard_server.ensure`, within 0.3 seconds) and, when none answers, starts one detached, never waiting for it (one bounded wait of up to a second for its state file, only when the budget allows). The ping carries an HMAC under the user key, a time and a nonce, and the answer must be the matching pong, so a listener that is not this user's server is ignored. The hook's JSON then gains the link with changes on in `systemMessage` only, never in `additionalContext`. A start that fails is one fixed line, "recortex: the live dashboard could not be started. Run hooks.py --doctor.", and `--doctor` names the reason. The prompt hook pings at most once in 30 minutes and shows the link only for the user's own `/recortex:dashboard`. Where no browser can reach a port (a remote machine reached over SSH outside VS Code), or when `"live_dashboard": false` or `RECORTEX_DASHBOARD=off` is set, nothing is started and nothing is shown.

### Safety

Every hook prints nothing and exits 0 when the project has no `.recortex.json` or its repository is not in the user's trusted list (see [session-protocol.md](session-protocol.md)). In a project that is set up and trusted, the SessionStart and SubagentStart hooks are never silent: when the brief cannot be produced (the local storage was refused, there is no index yet and GitHub cannot be read, any other error) they print one line, `recortex: record brief not shown: <reason>. Run hooks.py --doctor.` The other two stay silent then. None of the hooks writes to GitHub or blocks a session.

A project folder with a project file also gets a line shown to the user at session start (since 1.2.0), so that it is clear whether recortex is on. The SessionStart hook then prints one JSON object: `systemMessage` with the line, and `hookSpecificOutput.additionalContext` with exactly the text it printed before. The line uses fixed wording and holds no text from the record: `recortex: on. Record octo-org/sample-project, read just now.` (the age of the last sync when this start did not read GitHub, with `; GitHub could not be read now` when it failed), `recortex: on. The record of octo-org/sample-project is being read for the first time; the brief follows with your next message.`, or `recortex: off in this session: <the reason's fixed words>. Run hooks.py --doctor.` for a project file whose repository is not in the trusted list (no name is printed), whose hub is missing or unreadable, whose storage was refused, whose record has not been read yet, or after an unexpected error. The repository's name is printed only when it comes from a trusted project file and is a valid `owner/name`; the age comes only from a stamp of the UTC form. Claude Code shows the line at startup and after `/clear`, and does not show a new one when a session is resumed, so the status line segment (below) is what shows "on" then. A start after a compaction or a fork prints today's plain text and no line, since it repeats inside one sitting. On a fresh startup with a usable record, the line also tells the user how to open their project dashboard. A folder with no project file gets nothing new. To turn the line off, set `"notice": false` in the user's settings file (the one that holds `"discovery"`), or set `RECORTEX_NOTICE=0`: the hook then prints the plain text, byte for byte as before.

The hooks keep one small state file per project folder, `<state folder>/private/status/<first 32 hex digits of the SHA-256 of the folder's path>.json`, written at the end of the session-start and prompt hooks: `{"v": 1, "state": "on" or "building" or "off", "reason": a code or "", "repo": "owner/name" or "", "synced_at": a UTC stamp or ""}` and nothing else. The reason codes are `not-trusted`, `no-hub`, `storage`, `no-index` and `error`. `statusline.py` reads that file, and nothing else, to print `recortex on · read 2 h ago`, `recortex on · reading`, `recortex off · not trusted` and the like, `recortex · starting` in a folder with a project file that the hooks have not written their file for yet, but only while the JSON Claude Code gives the status line shows that no request has been answered (`cost.total_api_duration_ms` is 0, or `context_window.current_usage` is null); with no file and no such sign, or with a file that is there and fails its checks, it prints `recortex off · run hooks.py --doctor`, or nothing in a folder without a project file; it starts in about 15 ms and imports no plugin module. `setup.py apply` offers it (the answer `status_line`): with the user's yes it copies the script to `<config home>/recortex/statusline.py` and, when the user's `settings.json` parses and has no `statusLine`, adds `{"type": "command", "command": "python3 <that path>"}` and keeps every other key; when a status line exists already it writes nothing there and prints a snippet to combine the two. Nothing else in the plugin writes `settings.json`. The session-start hook replaces that copy when the plugin's file changes, and never creates one.

A third kind of text, approved field guidance, stands in its own frame in the subagent brief, between `BEGIN FIELD GUIDANCE` and `END FIELD GUIDANCE`. It is the short part of the project's field sheet, shown only when the repository is trusted, the user approved that exact text on this machine (its fingerprint is in the user's own configuration folder, which the project cannot write), and the text passes the sheet's form when it is shown. Every line of the frame starts with the plugin's own label, each value is one line of plain characters, and the frame's fixed note says it was approved by the user, cannot change rules, permissions or the task, and never makes a subagent count or report less than its material shows: what the material calls a failure is reported as one, every number the task asks for goes back to the session, and what the sheet's "Never write down" line names stays out of any draft or file that is to be posted or recorded, and comes back marked in the reply. In every other state (no sheet, turned off, marks only, changed since it was approved, not approved on this machine, refused by the form, approvals that cannot be read) subagents get the brief without it, and the session brief says in one fixed line why it is not shown; that line holds no text of the sheet. The prompt reminder and the compaction payload never mention it. A project with no `fields` entry gets one line at its next session start, once per project and machine, that offers to set the field.

Text that comes from GitHub or from the project sits between the `BEGIN PROJECT STATUS DATA` and `END PROJECT STATUS DATA` lines, which say it is data and not instructions; look-alike delimiters are defused and line breaks removed, and the brief is shortened to fit its size target without ever losing the END line. Outside the frame a payload prints only the plugin's own text, the trusted repository name, issue numbers, and the index time and issue links when they have the expected form. The hooks load only the profiles shipped with the plugin, never a profile file a project names, and keep only section headings and labels of a plain form. The `index.py query` text output starts with a line saying that what follows is data from GitHub, and prints each value on one cleaned line. The resume block passes the same author and edit checks as `resume_block.py show`; only a block that passed them when it was read is cached, and a cached block older than `resume_cache_days` (default 7) is left out when GitHub cannot be read. A brief built from the index after a failed sync says "cached, not refreshed" and how old it is. The index and the hook state are kept outside the project tree and are read only when the plugin made them for this user (see [session-protocol.md](session-protocol.md), "Security model"). An issue title is shown only when the issue was opened by an allowed account and no other account renamed it (the index reads each issue's rename history); otherwise the brief shows the number and "title not shown" with the reason.

### The first build and the background sync

Set-up runs `python3 scripts/index.py sync` once in the foreground, so the first session already has an index. When a session starts without a usable index (none yet, one refused and moved aside, an older format, or an empty one) the SessionStart hook does not try to build it in its few seconds: it starts a detached background sync and prints one line, `recortex: record brief not shown: building the local index in the background (first run); the brief appears at your next prompt. Run hooks.py --doctor for status.` Subagents get the same line while the build runs. Once the index is usable, the next UserPromptSubmit hook of that session prints the full SessionStart brief once (same frame and size cap), also when the one-line reminder is switched off, and then goes back to its usual behavior; the session state records that it did. If the build was stopped or killed, the next prompt starts it again. An incremental sync that does not finish within the SessionStart budget also continues in the background, so a large backlog catches up without holding up sessions.

Only one sync writes the index of a repository at a time, whether it is the session-start sync, a background sync, `index.py sync` run by hand or the rebuild of `compile.py`; a sync that finds the lock held stops with "another sync of this repository is running" (the session-start hook then uses the index as it is). The lock is a file `sync.lock` in the private folder holding the process number, host name, start time and budget; it appears whole in one step (a temporary file linked into place). A lock that is already there is judged by one process at a time, the one that makes the claim: a hard link `sync.lock.claim` to the lock, which only one process can make at a time. That process gives the claim a new time stamp at once, so a process that waits on an older claim, or that read the lock before, sees that this is another claim. It then reads the lock through its path, keeps the file open until it is done, and removes the lock only when it is stale, the path still names the file it read (device, inode and time stamp) and it still holds its claim; an open file cannot be given to a new lock, so two processes cannot both take the lock. No lock is renamed away. A claim that stands unchanged for about two seconds was left by a process that died, and is removed; a claim that is neither a file nor a symlink, such as a folder, is refused at once. A process killed while it held the claim, or just after it removed a stale lock, leaves its claim behind, and the next process that finds a lock in its way waits those two seconds once; with a `RECORTEX_HOOK_TIMEOUT` of 2 or less the wait outlasts the session-start sync's time: that brief is the cached one and says GitHub could not be read, and the background sync it starts removes the claim; with 3 the sync has half a second left. A stale lock that cannot be removed (on a file system whose file numbers cannot be compared) stops the sync with an error instead of reporting another sync, and the session-start hook says that the sync lock could not be taken. Three limits are accepted, in each of which two syncs can run at once: a sync that is still running past its time window and releases its lock at the moment another process removes it as stale; a process killed while it held the claim, when two or more processes then wait on that claim together, which is far more likely on a file system that keeps time stamps to the second, where a later claim looks like the one that was left; and a process that is held up for more than two seconds between its last check and the removal, whose claim is then taken for a left one and which removes the lock of the process that took its place. A lock with fields out of range, past its budget, or of a process on this host that is gone counts as stale; for a lock written on another host sharing the same home, only the time window counts. `index.py sync` run by hand stops after `--deadline` seconds (default 3600) and its lock lasts as long; a background sync is also stopped hard 45 seconds after its budget. The sync has its own budget, `background_sync_seconds` in `.recortex.json` (default 300, from 30 to 3600), logs to `sync.log` and records its outcome in `sync-status.json`, both in the private folder. It stores its progress page by page and issue by issue, so a sync that is stopped or killed goes on from there the next time instead of starting over. `hooks.py --doctor` shows whether a background sync is running (process number, start time), when the last one finished and with what result, the last error line of the log unless a background sync finished after it, a lock that is there but not live, and a claim that is there.

Two lines of 1.7.0 may follow the rest of a prompt of the main session, each of fixed words with numbers and checked addresses, and each with a cap of its own that takes no room from the setup reminder (the prompt payload's cap is untouched). The order is the prompt payload, the summary nudge, the dashboard line, the setup reminder, the task reminder. The dashboard line (320 characters) says that the user recorded a completed step, a map edit, a review verdict or an applied edit in the dashboard since the session's last prompt, with counts and at most six issue numbers, and to run `status.py --sync` and read them; the dashboard's local service leaves each as a small note in `dashboard-notes.json` beside the prompt state, each session is told once, nothing from before the session's start is told, and it is not printed when `prompt_hook` is off. The task reminder (900 characters) is [the reminder without the observer](observer.md); it is printed also when `prompt_hook` is off, and it works under a time limit. When its setting cannot be read, or the check raises, the session gets one fixed line once a session instead ("the task reminder setting of this machine cannot be read, so no reminder is added", or "could not be worked out for a prompt") that points to `hooks.py --doctor`; a check that raises also leaves the day for the doctor, and a check that works again clears it.

`hooks.py --doctor` ends with a block, "on this machine:", before its `problem:` lines: whether the record brief works, the task reminder (on, off, delivered by the observer, cannot be read, or on with the day its last check failed), the dashboard line (on, off, or on with the day a note could not be kept), notes (capture: ready, ready once a session has run here, or not ready with the code, the boundary and the command to run), whether the answers a session records can be read, whether the plugin's subagents could be measured, whether the observer's approval holds here (and what it is bound to, or why not) and the hosts (a fixed line on file locks; a second one where the mount keeps its locks on the host; one when another host's worker holds the folder). A part that cannot be worked out says "could not be checked". Fixed words, and codes from fixed sets: no path but the plugin's own script, and no name from the account database.

## The local index

`scripts/index.py` keeps a SQLite file at `$XDG_CACHE_HOME/recortex/private/<owner>__<repo>/index.sqlite` (by default under `~/.cache`); the hook state, the deliverable signals and the key are under `$XDG_STATE_HOME/recortex/private/` (by default under `~/.local/state`). Hooks, the session's Bash tool and your shell resolve the same paths, so the setup wizard's foreground sync, `compile.py`, `hooks.py --doctor` run from a terminal and the hooks all use one index. `CLAUDE_PLUGIN_DATA`, which Claude Code sets only for hooks, is not used; an index left there by an earlier version is ignored, and the first sync builds a new one. `hooks.py --doctor` prints the folders it resolved. Beside the index, for the manuscript: `texts/<issue>/<sha256>.md` (the text the plugin last wrote, so that the next write can tell what the author changed), `write/<issue>/<sha256 of the base>.json` (what `write.py start` decided for that base, with the resume state), `versions/<commit>/<issue>.md` (the vouched versions the mind page shows), and `versions/state.json` (the last refusal); each is private to the user, written atomically, validated when read and never echoed. `hooks.py --doctor` also prints the last refusal of a version, in fixed words. The record of deliverable signals already mentioned moved with this change from the index folder to the state folder, so a signal line already shown may appear once more after the update. It is never kept in the project tree, which a cloned repository controls. It is derived from GitHub and never edited by hand; how it is protected is under "Safety" above and in [session-protocol.md](session-protocol.md), "Security model".

| Command | Does |
|---|---|
| `index.py sync` | Reads the issues and comments that changed since the last sync, the timeline of each changed issue (labeled, unlabeled, renamed, closed, reopened, pinned) and its body edits, and the hub's resume block. Read-only on GitHub. `--deadline N` stops after N seconds and keeps what it has |
| `index.py sync --rebuild` | Starts from nothing; gives the same answers as an index built step by step |
| `index.py status` | Where the index is, when it was synced, what it holds |
| `index.py query consistency` | Candidates for review: the same quantity phrase with different values or denominators in different bodies; `#N` pointers to a missing issue, or written `#N (term)` where the target does not contain the term; bodies older than their newest result, decision, failure or correction; section labels that disagree with headings; figures and tables without a Sources row |
| `index.py query impact --path P` or `--commit C` | Every section, figure, table, Sources row and event comment that cites a file or a commit |
| `index.py query timeline [--issue N] [--type T] [--since D]` | Every event comment and issue event in time order |
| `index.py query recall --issue N` | For a new memory on issue N: the 12 newest memories of its thread (the issues that share a `topic:` label with N, or N alone), each with id, date, kind, state and plain line; up to 12 open questions and untried ideas of other threads; up to 40 words explained so far; what the thread is about, or that nobody has written it yet. Only memories of allowed accounts when the repository is trusted, with a count of the others; every text is cleaned and printed under the data line |
| `index.py query mind` | What the mind page tells, as one line of counts: memories told, threads, words, open thoughts, and how many are not told and why. `--json` prints the whole model the page is made from. Only for a repository in your trusted list ([mind.md](mind.md)) |
| `index.py query triage` | Open issues with no role label (`hub`, `final-record`, `active`, `triage`) and no closed-out type (`type:duplicate`, `type:out-of-scope`): issues people opened by hand |
| `index.py query tasks [--json]` | The open tasks with their steps, each with its state and the memory that checked it; a task's title only when it is told. Under the data header |
| `index.py query find --words "..." [--issue N]` | The ranked packet of what the record holds on those words (as the observer's context packet is built), as quoted data under the data header. Read-only; it needs no observer |
| `index.py query brief` | The four hook payloads |

The index holds issues, comments and issue events as GitHub returned them, and derives from them: labels (role, section, topic and `type:` labels alike), the sections of each body, events (type, time, recorded time, reconstructed or not), figure and table blocks, Sources rows, the paths, commits, pull requests and URLs each section and event cites, candidate numbers, `#N` pointers, and which body edit followed which event. Number extraction is a heuristic: the consistency query reports candidates and never changes a body.

Two more tables, `steps` (`comment`, `issue`, `ordinal`, `text`: each numbered step of a `steps` memory) and `marks` (`source`, `kind`, `target`, `step`: each `done=` or `dropped=` group of a marker), are derived with the four below and covered by the same `mind_derived` triggers. `derive_version` is `5` since 1.5.0, so the first sync after the update derives every comment again from the stored bodies, with no network. Which steps stand and which are done is decided when they are read (`task_rules.py`, [tasks.md](tasks.md)), never when they are stored.

Four more tables keep what memories say, row by row per comment: `links` (each link of a marker as written, with no check of its target, so a target that arrives with a later sync counts from then on), `event_fields` (each field in order, the plain line under the label `plain`; the Evidence field is left out), `evidence` (each Evidence line in one of the four forms, of a result, decision, failure or correction that is not reconstructed) and `explanations` (each well-formed fold). What counts is decided when they are read: a link counts when both ends are memories in the index, the memory that carries it was written by an allowed account and is not reconstructed, its target is not later and the kinds may be linked ([issue-model.md](issue-model.md), "Links between memories"); a memory's state (replaced, set aside, answered, tried, taken up, open, untried, stands) follows from the counted links that point at it. A malformed link value, an unknown marker key, a fold that does not match its form or an Evidence line of another form is ignored, and the comment stays an event of its type. No hook reads these tables: the payloads hold no text of a memory. The startup notice points to the dashboard command. Only an explicit request builds [the page](mind.md) beside the index. A memory that was changed on GitHub after it was posted is not told when the repository is trusted, unless its edit history shows only edits by allowed accounts (below): it is then left out like a memory of another account, its links do not count, its folds explain nothing, and `query recall` says how many it left out. The timeline rows of `query timeline --json` and `compile.py` carry each memory's id (`comment`), plain line and links as written.

Two more tables, `comment_edit_reads` and `comment_edits`, keep who edited each memory that looks edited (its comment's `updated_at` differs from its `created_at`). The sync reads the history of such a comment, and only of such a comment, from GitHub in one GraphQL call per 40 comments (`node(id:)` with the comment's node id, which the comment listing gives; a comment stored by an older version costs one REST read for it), and one more call per 40 for each further page of a long history. `comment_edit_reads` holds the node id, the `updated_at` the history was read for (`stamp`), the number of edits besides the creation, GitHub's `lastEditedAt` and whether the read was whole; `comment_edits` holds each edit's time and editor (empty for an account that is gone). A read counts only while its stamp equals the comment's current `updated_at`; it clears a memory only when every editor is allowed when the index is read. An edit history of topic text is read the same way, every page. Versions before this one do not know the two tables and leave them alone; a comment they rewrite carries a new `updated_at`, so the stored history no longer counts until the next sync reads it again. A rebuild empties and refills them. A comment that GitHub cannot resolve is stored as unreadable for its `updated_at` and not asked again, so a passing failure of that kind leaves the memory untold until it changes or `sync --rebuild`.

Two versions of the plugin on one machine use one index. A version before 0.6.0 does not know the four tables and leaves them alone; when it writes comments or events, a trigger that this version made sets `mind_derived` in the index to 0. This version derives the four tables only when it was the last to write comments or events: anything but 1 at the start of a sync makes that sync derive everything again, which also restores the type of ideas and questions that the older version stored as `other`. Until then `query recall` prints one line, "the index was last written by an older version of the plugin, or never by this one; run index.py sync", and stops, and the timeline leaves its three columns empty.

From 0.9.0 the index holds three more tables, all derived or read and all rebuilt by `sync --rebuild`: `parents` (the sub-issue parent of each issue, read in the same GraphQL batch as the body edits), `pull_merge` (whether each pull request was merged, from the `merged_at` of the issues listing, with the `updated_at` it was read at: a merge that an older version stored on a shared index is read again, and a closed pull request with no merge state waits for the next sync) and `board_cards` (the cards of the board, only when a board is configured and approved; see [board.md](board.md)), and the meta keys `resume_url` (the address of the checked resume comment), `board_error` (a fixed reason code or empty) and `board_read_at`. An index from before 0.9.0 lists the issues and reads the body edits again once (the meta key `links_ready`). The board is read in the last step of the sync, which writes nothing to GitHub and never makes the record's sync incomplete; when the budget is spent the cards of the last read stay, `board_error` says "budget", and the session start hands the board to a background sync; a project without a board makes no call for it. The brief gains one line inside its data frame (`Board: 2 cards were moved by hand: #7, #13. Run board.py plan.`) and, when the board could not be read, one fixed line outside it; neither appears for a project without a board, whose payloads are unchanged.

The SessionStart hook gives the sync half of its time limit (`RECORTEX_HOOK_TIMEOUT`, default 10 seconds, digits only), stops calling GitHub once that is spent, and reads the hub's resume block, at most ten issue timelines, one GraphQL batch of body edits (up to 40 issues, every page of their histories) and one batch of memory edit histories (up to 40 memories, each without a stored node id costing one REST read) and, when a board is configured, one board read per session start (the last step, after the edit histories); the rest continues in a background sync, and the brief, which then says "partly refreshed", is built from the index in the remaining time. On a large tracker, run `index.py sync` once by hand to fill the index. A sync that reaches its deadline keeps and derives what it read and the next sync goes on from there; one that reaches it while it reads the hub keeps the cached resume block and counts as stopped at its budget, not as an error, and a read of the hub that fails also leaves the cached block in place; the index counts as synced (its time in the brief) only after a sync that read everything, so a brief built after an unfinished sync says "cached, not refreshed". An incremental sync reads what changed since the newest time it has seen, less one minute, so items stamped in the same second are not missed; it does not see issues or comments deleted on GitHub. `index.py sync --rebuild`, and `compile.py` by default, read everything again. A comment without an event marker is ordered by the date and time of its heading: a zone abbreviation that `zones.py` knows (PST, PDT, CET, UTC+2 and the like) is converted by its own offset, and a zone it does not know falls back to the time GitHub gave the comment; the marker gives the exact time.

### The tasks lines

Since 1.5.0 the sync keeps one more meta key, `task_counts`: JSON of six integers (`tasks`, `steps`, `done`, `next_task`, `next_step`, `hand`), worked out from the index and never from GitHub; `hand` counts the open tasks whose list in the body was changed by hand. The hooks read that key, every value an integer from 0 to 99999 (anything else gives no line), and print, outside the data frame:

| Case | Line |
|---|---|
| open tasks that have steps | "Tasks: 2 open, 7 of 12 steps done; next: step 4 of #14." |
| a list changed by hand | "Tasks: 1 list was changed by hand on GitHub. Load the recortex skill and run its tasks.py status." |
| open tasks with no memory in 14 days | "N tasks had no memory in 14 days: #12, #15." (at most 10 numbers) |
| topic bodies older than their newest result | "N topic bodies are older than their newest result: #5, #6." (bodies outside the paper's plan are reported, never edited) |

Inside the data frame, through `brief.defuse()`, the brief lists at most 5 lines "- #14 step 4: (text)", the next open step of the open tasks, from told `steps` memories only. These lines give way before any other list when the session-start payload nears its 6,000 characters. The prompt reminder gains "; steps: 7 of 12 done", dropped first if the payload would pass 400 characters, and the status line gains " · steps 7/12" from two checked integers in the state file. A project with no task prints none of them, and `hooks.py --print` and `--doctor` cover them. A step's words are text from the record, so they stay inside the frame; nothing else about a task reaches a payload.

### The observer's lines

The observer's own handlers (`run_observer_hook.sh`) print more fixed lines, made of fixed words and integers: that anything waits for the user's answer, at session start and as a reminder at the next prompts ("recortex observer: N items wait for the user's answer. Load the recortex skill first, run its observer.py pending --waiting, ..."), that a draft of the paper's text waits, what the observer did since the last notice (the acts line, at most once in 6 hours per session), that its log of acts could not take an act (one line with a whole number, at most once a day while it keeps failing, pointing to `hooks.py --doctor`, which prints the count and the day of the last failure), and, for a folder enabled before 1.5.0, that the observer is paused until a level is chosen. A title, a step or a plain line never enters one of them; the questions that carry them are shown in the dialog ([observer.md](observer.md), "What waits for your answer"). Each line a hook returns is counted in `usage.db` by its characters, as an estimate.

The reminder about a changed decision (the return pointer of a session start or of the first prompt of a session, and the observer's pointer on a prompt) is worked out under its own time limit: 2 seconds at a session start and 1 second at a prompt, and never more than a fifth of the hook's budget; the observer's is 1 second of its 3.5. A record too large to check in that time costs the reminder only. The hook keeps the rest of its brief or context, prints one fixed line that says the reminder was left out (the line holds no text of the record), and `hooks.py --doctor` prints when a hook last did so, which hook, and the time it had.

### The plan lines

Every sync also keeps two meta keys for the status summary: `resume_posted` (when the newest allowed, never edited resume block was posted, in UTC) and `summary_state`, JSON of two values, `since` (an integer: the told memories whose comments are newer than that block) and `posted`. The hooks read `summary_state` only in that form (an integer from 0 to 99999 and a time in the one form the sync writes; anything else gives no line). The `UserPromptSubmit` hook adds one fixed line, `recortex: the project's status summary is out of date (N memories recorded since the last resume block). At a convenient point post a new resume block with a fresh In short, and do what else is due: the board's apply, the planner's due check, the next actions.`, when `since` is 5 or more, or when the block is a day old and `since` is at least 1; at most once every 6 hours for a session, kept as a number in the session's state; and never when the observer is on in automatic mode, whose worker refreshes the summary instead. The line holds fixed words and one integer; nothing of the block or of a memory is in it. The session-start brief carries the block, In short first, inside the data frame under its cap, and the compaction payload tells the session to keep the summary.

For a project whose profile has a plan (the manuscript profile) the sync keeps one more meta key, `plan_counts`: JSON of ten integers (`issue`, `parts`, `against`, `moved`, `unbacked`, `unused`, `limits`, `due`, `proposals`, `texts`), worked out from the index by `index.py` and never from GitHub, or empty. The index version goes up with the kinds `plan` and `text`: a meta key `derive_version` says which rules derived the stored comments, and the next sync derives every comment again from the stored bodies, with no network, when it is missing or differs, so that an index an older version synced tells plan comments as plans after one sync. No table or column is added and `FORMAT` stays "2"; an older version that syncs the same index writes comments and events again, which clears `mind_derived` and `derive_version` (triggers of 1.3.0), and the next sync of this version derives every comment again.

The hooks read `plan_counts` (every value an integer from 0 to 99999; anything else gives no line and one line in `--doctor`), the project's `plans` and `planning` entries, and the user's own `settings.json` (`"planning": false` there or in the project file switches the lines off; no file can switch them on). They print, outside the data frame and beside the board's line, fixed wording, one checked issue number and integers:

| Case | Line |
|---|---|
| a plan-capable profile, no `plans` entry, and the record holds a finding or a topic with text | "Plan: this project writes a paper and has no plan for it yet. Start the plan run ..." at every session start, until a plan issue exists or planning is off |
| a plan that has a finding against a part, a part that rests on something that changed, a stated limit that is not planned, or three findings used by no part | "Plan of the paper (#12): 9 parts; 1 has a finding against it; ... Bring the plan up to date now ..." |
| a plan in step | "Plan of the paper (#12): 9 parts, in step with the record." |
| a `plans` entry that names an issue the sync cannot use (not in the index, no label `plan`, opened by an account that is not allowed) | one fixed line that points to `hooks.py --doctor` |

The prompt reminder gains "; plan: 1 part has a finding against it" while that count is above 0, the subagent brief "The paper has a plan (#12).", and the compaction payload lists the plan issue among the issues in play. These lines are never cut when the session brief nears its cap; the lists of topics and active issues give way first. No planned statement, no proposed text, no login and no path ever enters a payload. A project without a plan-capable profile gets the payloads it had. `hooks.py --doctor` prints the counts, whether planning is on and what is wrong with them.

### The writing lines

For a project with a plan the hooks also read the writing mode of this machine (the user's `private/writing-modes.json`, read only, nothing created) and the project's `own_manuscript` entry, and print, in the same place, fixed words and integers: "Writing: the user has not chosen whether recortex writes the paper's text. Ask once with the multiple-choice prompt (review, autonomous, off), then run setup.py writing set." at every start until the user answered, but only when the setup questions are switched off (otherwise this question is one of the setup questions, [below](#the-setup-questions-line)); one fixed line, pointing to `hooks.py --doctor`, when the setting cannot be read (it counts as off); and, when the mode is review or autonomous and any count of `plan_counts` is above 0, "Writing (review mode): 2 parts of the text are due; 1 proposal waits on GitHub; 3 text changes were written since the last pause. Follow \"Write the text\" in the recortex skill." The counts `due`, `proposals` and `texts` come from `write_rules.py`. When parts of the record's text changed since the author last brought them into their own paper, one more line says how many ("Your own paper: 2 parts of the record's text changed since you last brought them into it ..."); it holds integers only, never the path, and a part never brought over is not counted. The hooks never open the author's file, never write to GitHub and never contact the branch of versions.

### The setup questions line

At session start, after the brief and before the line about a new deliverable and the offer to set the field, the hook may print one fixed line (since 1.4.0): "recortex: 2 setup questions to check, added since this project was set up. Before your first reply ends, once the user's request is done (at once for a greeting, an open question or a prompt about recortex), load the recortex skill, run its setup.py questions and ask what it lists as one multiple-choice batch, as the skill's "Setup questions" section says. Do not offer the questions in prose." It holds a number from 1 to 6 and the plugin's own words, and it is shown once per session id (`asked` in the session's entry of `prompt-state.json`, marked before the line is printed; the brief's lists and resume block are shortened to make room for it, so that a full brief still carries it; with no session id it is shown each time). A second fixed line, "recortex: the setup answers of this machine cannot be read, so no setup question is asked. Run hooks.py --doctor.", is printed at every session start while `private/setup-answers.json` cannot be read and a question would be open without it. No other payload carries either line, nor do `hooks.py --print` and `index.py query brief`. The prompt hook adds a third fixed line, with a number from 1 to 6, to a later prompt of a session that has not run `setup.py questions` since it started: "recortex: 2 setup questions still open, and setup.py questions has not run in this session. Before this reply ends, load the recortex skill, run its setup.py questions and ask what it lists as one multiple-choice batch, as the skill's "Setup questions" section says. Do not just offer the questions." It is given from the second prompt on, while a question is open (counted from local files, with no GitHub call), at most three times a session and three prompts apart, only when it fits what is left of the payload's cap (400 characters), never with the prompt hook off, the setup questions switched off or no session id, and its marks (`reminded`, `reminded_at`, and the session's `start`) are saved in the session's entry of `prompt-state.json` before it is printed; `setup.py questions` notes when it ran in `setup-questions-run.json` of the same folder.

The count is made from local files only and prints nothing it read: the project file the hook parsed, the index (the plan counts), the writing modes, the answers of this machine, the user's Claude Code `settings.json` (is there a `statusLine`; a symlink, a file over 1 MB or one that is not a JSON object counts as nothing to ask) and the observer's approvals. The hook makes no GitHub call: the question about the labels is counted as one to check, and `setup.py questions` settles it. While the question about the manuscript profile is open or deferred, the line about new paper files is not printed. Any other failure gives no line, and the brief is shown as usual; `hooks.py --doctor` prints one line with the open, answered and deferred ids and why the others are not asked. Off with `RECORTEX_SETUP_QUESTIONS=0` or `"setup_questions": false` in the plugin's `settings.json`. See [setup.md](setup.md), "Questions added after setup".

## Compiling the deliverable and the history

`python3 scripts/compile.py --out <folder>` rebuilds the index from GitHub, so that deleted issues and comments are not compiled (`--incremental` syncs only what changed and does not see deletions; `--no-sync` uses the index as it is). A rebuild reads both listings first and replaces the stored ones in one transaction, so a rebuild that cannot reach GitHub leaves the index as it was; it costs one timeline call per issue and pull request plus one GraphQL call per 40 issues, and writes:

| File | Holds |
|---|---|
| `deliverable/NN-<label>.md` | For each deliverable section, in the hub's order, the text under that section's heading in each topic body that carries its label, in the hub's topic order, each under a topic heading with the issue link |
| `deliverable/figures.tsv`, `tables.tsv` | Every figure and table block: id, issue, title, section, caption, image or file at its ref, data file, command |
| `deliverable/sources.tsv` | Every Sources row with its topic |
| `history/timeline.tsv`, `timeline.md` | Every event comment and issue event in time order: time, type, issue, issue title, labels, title, author, link, recorded time, reconstructed, and for a memory its comment id, plain line and links (`timeline.md` shows the plain line under "In plain words"). A comment that is not a typed event is kept with type `other` |
| `MANIFEST.json` | Repository, hub, time of compilation, time of the index, counts, and the `--ref` given |

`--dry-run` lists what would be read and written and reads nothing from GitHub. Files of the same name are replaced; nothing else in the folder is touched.
