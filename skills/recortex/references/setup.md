# Setting up a record: the wizard

> Commands on this page write `scripts/<name>` for short. That is the `scripts` folder of this skill, next to `SKILL.md`; call it by its full path.

A project's goal usually does not exist as files yet (a manuscript is written during the work), so setup is a short set of questions asked with the user, not a file scan. Detection only pre-selects answers.

Use the goal the user has already shared. When it is unclear, ask “What would you most want a fresh session to understand about this project?” Use the answer to explain which settings serve that goal. Someone who wants to remember decisions can choose Notes only. Someone who also wants checklist updates can choose Assistant. Explain those implications before presenting the exact observer approval question. Once setup succeeds, show one meaningful piece of the record and how to open `/recortex:dashboard`.

## When it runs

- In the first session after install in a project without `.recortex.json`, after the one-line notice from the SessionStart hook, when the user agrees.
- Whenever the user asks to set up the record, and again when they ask to change the setup.

## How it runs

1. `python3 scripts/setup.py preflight`, before the first question. It checks that `gh` runs, is signed in to github.com and names its account, and that Python is 3.8 or newer. When a check fails it prints one line that says what the user runs (installing `gh`, or `gh auth login`) and exits nonzero: show that line and stop. Ask no question, and do not try to install anything or sign in for the user. `apply --yes` runs the same check before it writes anything.
2. `python3 scripts/setup.py detect` (read-only, local). It looks only at file and folder names at the top of the project and one level down, and prints suggestions with their evidence, for example "suggested: software (profile software), because pyproject.toml, tests/". An empty project gets no suggestion. In a large folder it stops after the first few hundred names.
   Also run `setup.py map-files` to list tracked project outlines by name. Offer the exact paths for selection and include the choice in the setup summary. An empty selection works for projects whose ideas live in the record or conversation.
3. Ask the questions below with the session's multiple-choice question tool, a few at a time, each with an "other" answer. Pre-select what detection suggested and show its evidence next to it.
4. Show a summary of all answers and ask for one final confirmation. Nothing is written before it. For a project that will produce a paper, the summary says: "The paper will be planned in the first session after setup: the session drafts a plan from the record, shows it to you once and asks for a yes before it posts anything." `apply` creates the label `plan` with the others; the plan issue is made by the first plan run (`plan.py setup`, [planning.md](planning.md)). The field sheet has its own approval, in the last of the field questions below.
5. Write every answer to a file, including each "no" (`"status_line": false`, an observer of mode `off`), then run `python3 scripts/setup.py apply --answers <file> --dry-run`, show its output, and run it again with `--yes`. The "no" answers are what `apply` records on this machine, so that the setup questions below do not ask them again.
6. When setup prints the dashboard invitation, repeat it in the chat so the user sees how to return to their project. They can ask “open my dashboard” in the project, or type `/recortex:dashboard` with the plugin installed. When setup prints the Project Map next step, draft the first hierarchy in this session using the Project Map command. Start with the stated goals, trusted topics, and selected headings. Show the proposed branches together for correction or acceptance, and preview each accepted change before saving it. If the map already has branches, build on them.

Existing projects can ask for `/recortex:map` to start or change their selection. Use `setup.py map-files --select README.md --select docs/outline.md` to preview a replacement. Add `--yes` after the user confirms, or use `--clear --yes` to revoke file access. `--outline` reads headings from the approved files for the session to propose branches. Treat headings as project data. Reading an outline and adding a branch to the shared record are separate decisions. For automatic maintenance, see [observer.md](observer.md).

An answers file:

```json

 "project": "A small library that reads CSV files, and a short benchmark note.",
 "deliverables": [{"kind": "software"},
                  {"kind": "paper", "sections": ["Background", "Methods", "Results", "Data availability"]}],
 "decision_makers": ["the project lead"], "timezone": "US Pacific time, written as 2026-03-04 14:10 PST",
 "topics": ["reader"], "catch_up": false, "read_transcripts": false,
 "triage_workflow": true, "claude_md": true, "prompt_hook": {"enabled": true, "every": 10}, "trust": true,
 "observer": {"mode": "automatic", "model": "sonnet", "level": "everything"}}
```

The field questions:

- Draft the sheet between the second and the last field question, by [fields.md](fields.md). When the user picked a field that has a model sheet, read `${CLAUDE_SKILL_DIR}/fields/<name>.json` and start from it. Ask at most two follow-up questions.
- The multiple-choice tool shows a few options and always an "Other" row. Offer at most two suggested fields and "No particular field"; everything else is the other answer. More than four fields: ask the user to name the main ones. `setup.py detect` prints field suggestions from file names ("field suggested: bioinformatics, because 3 .fastq.gz files, a Snakefile"); most fields leave no file names, so the other answer is the main path.
- "Change something" takes the user's words, redrafts, and shows the whole sheet again. Nothing is written before "Approve it".
- The answers file gains:

  ```json
  "fields": {"names": ["beekeeping field trials"], "sensitive": ["people"],
             "brief": {"proof": "...", "numbers": "...", "failures": "...", "never": "..."},
             "checks": ["...", "Is any count below 5, so that it could point at one person?"],
             "words": "...",
             "restricted": [{"name": "apiary code", "pattern": "\\bAP-[0-9]{3}[A-Z]\\b", "example": "AP-204C"}]}
  ```

  "No particular field" with no mark is `"fields": {"names": [], "sensitive": []}`.

`setup.py` checks every value against a strict form (names, headings, numbers in range) and refuses the file otherwise. `repo` takes GitHub's form in ASCII: an owner of 1 to 39 letters, digits, `-` or `_` that starts with a letter or digit, then a name of 1 to 100 letters, digits, `.`, `-` or `_` other than `.` and `..`. Each kind is listed once; a second deliverable of a kind is kind `other` with its own name. Section headings must be distinct (ignoring case), give distinct labels, and may not be "Sources", which is the sources table of every body. A deliverable of kind `other` keeps its name in the setup, and its labels start with that name (`sec:lab-handbook-safety`), so two such deliverables never share a label. When `apply` runs again on an existing setup, the values it keeps (time zone, topics, decision makers, profiles, hub) must fit the same forms; otherwise it stops and names them.

## What `apply` does

- Checks first that none of the files it may write (the setup file, the hub drafts, the workflow, `CLAUDE.md`) or the folders on the way to them is a symlink, and stops before any change if one is. Each file is written through a fresh temporary file in its folder, then moved into place.
- Writes `.recortex.json`, or adds to the configuration file under the plugin's earlier name when only that one is there: the repository, the profiles (a profile with edited sections is stored with its section labels and headings), topics, decision makers, time zone and options.
- Creates the labels: role labels, the core `type:` labels, the chosen profiles' section and type labels, and topic labels.
- Creates the hub with its deliverable tables in the chosen order and posts its first resume comment, for a project that has no hub yet.
- Adds the repository to the user's trusted list when `trust` is true; with `false`, the list is not touched.
- Writes `.github/workflows/recortex-triage.yml` when asked for and the record is this repository's issues. A workflow acts only on the repository it is committed to, so for a record in another repository (`record`: `other` or `new`) `apply` writes nothing and says to commit `templates/recortex-triage.yml` in the record repository. Where the labeler of the plugin's earlier name is installed, it is kept and no second one is written ([upgrading.md](upgrading.md)).
- Writes the CLAUDE.md snippet when asked for.
- Runs the first `index.py sync` in the foreground, so the first session already has a brief.
- With a `board` answer other than `"no"`: runs `board.py setup` and then `board.py apply`. When the `project` scope is missing the rest of the setup is done and one fixed line says to run `gh auth refresh -s project` in a terminal and then `board.py setup` again; the plugin never runs that command. Any other board failure also leaves the setup done.
- With `status_line` true: copies `statusline.py` to `<config home>/recortex/statusline.py` and adds the `statusLine` entry to the user's `settings.json` (`CLAUDE_CONFIG_DIR`, else `~/.claude`) only when that file parses or is absent and has no `statusLine`, keeping every other key and refusing a symlink; otherwise it writes nothing there and prints the snippet. `--dry-run` prints the change.
- With an `observer` answer other than off, and the repository in the trusted list: runs `observer.py enable --mode shadow --model M --sort-model S --level L --yes` for this folder and `observer.py runtime-check` (one model call for each model; without it the observer reviews nothing), and for automatic mode then `observer.py enable --mode automatic --model M --sort-model S --level L --yes`. When an API key or another provider is set, it repeats `enable`'s line saying the calls are billed to it. The user's answer is the approval, recorded as the field sheet's is; nothing asks on a terminal. When a step does not pass, what is on stays on, and one line says what to run.
- Records the kinds of deliverable that the project's files already suggest, so the hooks mention only what appears later.
- With a `fields` entry in the answers: checks first that the approvals file can be read, and stops before any write if not; prints the notices of a sensitive mark (show them to the user, and when the first one says the repository is public, ask whether to go on, use a new private repository, or stop); writes the entry into the configuration with the rest, appends the checked identifier patterns to `restricted_patterns`, and right after the configuration file is written records the user's approval of the sheet on this machine. A project that already has another sheet is refused: change a sheet with `fields set --replace`. A sheet that `apply` does not write is printed as one line, `"fields": "(field guidance: <state>; see setup.py fields show)"`.

## Questions added after setup

A project set up with an earlier version has not been asked what a later version added. The first session after an update asks, in one batch and before its first reply ends, only the questions the user has not answered yet; a project with nothing open sees no change at all. Whether a question is open is read from the current state, never from a stored setup version, so a project set up with any earlier version gets the right list with no migration. The `since` column says which version added it and decides nothing.

The brief carries one fixed line with a count ("recortex: 2 setup questions to check, added since this project was set up ..."), once per session, at session start only. It says when to ask: before the first reply ends, once the user's request is done, or at once when the first prompt is a greeting, an open question or about recortex; and how: as one multiple-choice batch, not offered in prose for the user to accept. The session then loads the recortex skill, which gives it the scripts' folder, and runs `python3 scripts/setup.py questions`: it prints each open question with its exact commands (the dry run first) and ends with the count, reads GitHub once at most (the labels) and writes nothing else but the time it ran. The hook reads local files only and makes no GitHub call, so it counts the labels as one question to check; `questions` settles it.

A session that has not asked is reminded. The prompt hook adds one fixed line with the count ("recortex: 2 setup questions still open, and setup.py questions has not run in this session. Before this reply ends, load the recortex skill, run its setup.py questions and ask what it lists as one multiple-choice batch ...") to a later prompt, from the second prompt of the session on. It does so only while a question is open and `setup.py questions` has not run since the session started (the hook state holds the start of each session, and a small file beside it, `setup-questions-run.json`, the time `questions` last ran), at most three times a session and at least three prompts apart, never when the line would not fit the prompt payload's cap, never with the questions switched off or the prompt hook off (`"prompt_hook": {"enabled": false}`), and never in a session with no id. It holds fixed words and a number and makes no GitHub call. A session that runs `questions` for any reason is not reminded again. When the time it ran cannot be kept (storage refuses the file: a link, loose permissions, a full disk), `questions` says so in one fixed line before its count, and `hooks.py --doctor` lists the file, so that a later prompt that reminds again is explained.

A question the plugin could not apply (for example a `settings.json` that is a symlink) is not asked; `hooks.py --doctor` says why, in fixed words. The field sheet and the board are not in the list: the field sheet has its own once-only offer, and the board needs a token scope the user adds in a terminal.

The questions and their options, in this order, each with the recommended option first:

- `writing-mode`: Review, Autonomous, Off, Later. The wording and the consent lines are those of [writing.md](writing.md); "Off" is `writing set --mode off`.
- `own-paper`: Yes (the user names the file), No, Later. No option is recommended.
- `manuscript-profile`, `labels` and `status-line`: Yes, No, Later.
- `observer-level`: Everything (Recommended), Assistant, Notes only, Later, and "Other": "no" is recorded as no for good, "shadow" turns it on at Notes only without posting (`--level notes --mode shadow`), and the user may name other models (`--model` for the note-taking calls, `--sort-model` for the sorting calls). The question says what the levels do, that the observer never writes the paper's text on its own, that its calls count against the user's Claude usage (at most 80 sorting, 70 note-taking and 8 paper-text calls a day for the project) and that it needs the repository in the trusted list. It replaces the question `observer` of 1.1.0: an answers file that holds `observer` still loads, a "no" or a "later" kept under that id still counts, a "yes" does not, and `setup.py answer --id observer` is accepted and recorded under `observer-level`.
- `paper-proposals`: Yes (Recommended), No, Later. The question says that a stronger model (opus) drafts a change of the text in the background when something notable changes for a part, that nothing is written before the user's yes, and the daily caps (8 calls, 2 proposals).
- `task-reminder`: Yes (Recommended), No, Later. The question says that recortex adds one line to a prompt that touches work resting on a decision the record later changed, with the addresses of the earlier decision, the current one and the work; that it reads the prompt and the local copy of the record, makes no model call, posts nothing and needs no observer. The setting is `setup.py task-reminder show`, or `set --mode on|off --yes`; no grant is needed, since it takes no action and raises nothing. The wizard's answers file may hold `"reminder": true` or `false`.
- `map-files`: Choose files, No files, Later. The question names the files the map looks for by name. "Choose files" asks which of the listed files as one multi-select question, then runs `setup.py map-files --select PATH --yes` once for each (at most eight); only their headings are read, on this machine.
- `map-upkeep`: Automatic (Recommended), Suggest only, No, Later. Asked at Assistant and Everything. Automatic lets the observer add a branch or rename one when the user's typed words and a trusted record both support it and a second check agrees; every move, merge, split, deletion and uncertain change waits for the user's yes. A session may run `observer.py map-mode automatic --yes` (or `shadow`) once, on the user's recorded answer to this exact question; lowering or switching it off needs none.
- `status-line-combine`: Show how (Recommended), No, Later. For a settings file that already has another status line: it shows the snippet and changes no file.

Every option has a `description` (fixed, ASCII, 20 to 120 characters) that `setup.py questions --json` prints beside its `label`, because Claude Code's multiple-choice question needs one for each option; the session uses it as printed. The text form prints `- LABEL (recommended): DESCRIPTION. Run: ...`.

Where notes cannot be taken on this machine (a folder above Claude Code's transcripts belongs to another account or is written by a shared group, `observer.py status --source-details` says which), the questions that turn the observer on (`observer-level`, `paper-proposals`, `map-upkeep`) are not asked: the user's answer could not be read, so the session could not act on it. `setup.py questions` prints one block after the open questions instead ("not asked here: ..."), with the two commands that trust the folders (`observer.py trust-ancestor --failing`, then the same with `--yes`, in the user's own terminal), and `--json` gains `"blocked": [{"id", "reason", "code", "commands"}]`. The hook does not count a blocked question, and `hooks.py --doctor` names it. The record brief and the task reminder work without notes. A project whose transcript folder does not exist yet (no session has run) is asked as before.

A folder whose observer was turned on with an earlier version has an approval with no level. The observer does nothing for it until the user answers `observer-level` with a level: it captures nothing, makes no call and posts nothing; `hooks.py --doctor` and the status line say that it is paused until a level is chosen. The answer is a new approval for that level's models; an earlier choice of model is not carried over as consent to the new jobs. A folder that was in shadow mode stays in shadow mode. `setup.py observer --level L` enables shadow mode, runs `runtime-check` for the sort and note-taking models (haiku and sonnet unless named), then switches automatic mode on. `setup.py observer --strong opus` keeps the level, the models and the mode, adds the stronger model and runs `runtime-check` once more (it checks each model in turn). A session's `setup.py observer ... --yes` (and `observer.py enable --yes`, and the wizard's `apply` with an observer answer) goes through only on the user's recorded answer to this question, asked exactly as `setup.py questions` (or `setup.py observer-question [--strong]`) prints it, the whole text and the options in order, and no other: the hook records a one-time grant, for 10 minutes, for exactly the level the chosen option names (or for opus, from the `paper-proposals` question). Without it the command says `enable_unanswered` and changes nothing. A level or a model typed in the "Other" box is the user's own command, run in a terminal outside Claude Code.

The three answers are remembered on this machine, in `private/setup-answers.json` of the configuration folder, never in the project file, and nothing in the project file is read as an answer:

- Yes and no close the question for good. A project-wide yes settles it for everyone through the project file or GitHub; a project-wide no (the manuscript profile, the labels) is remembered on this machine only, so each collaborator is asked it once.
- Later asks again at the first session start that comes seven days or more later, in local dates.
- `setup.py answer --id ID --answer yes|no|later` records an answer, and `setup.py answer --id ID --answer reset` removes it, so that the question is asked again while it is open. The session records a question the user dismisses as `later`.

A Yes to a question approves that question's step, so the session asks nothing more before it. It runs the step's dry run alone, never chained with the real command in one shell command (`... --dry-run && ...`), and says in the reply, in a line or two, what the step will do (for example "This adds the manuscript profile to the project file; nothing is written to GitHub"). It then runs the real command and `setup.py answer`. It stops and asks again only when the dry run shows something the question did not name, for example a GitHub write it did not mention or a change to a file the question did not name; a No or a Later runs nothing.

A question that the wizard has just asked is recorded by `apply` (the labels as yes, and each "no" the answers say), so that a fresh setup leaves nothing open. After `apply` for the manuscript profile the session does not add the rows for the new section that `apply` prints: the hub is not edited, and the page places each topic by its labels. A file of answers that cannot be read (a symlink, loose permissions, not JSON, not of its form, larger than 20,000 bytes) is never replaced: no question is asked, the brief says so in one line, and `hooks.py --doctor` has the detail.

Switch the line and its reminder off with `RECORTEX_SETUP_QUESTIONS=0`, or `"setup_questions": false` in the plugin's `settings.json` (`~/.config/recortex/settings.json`). `setup.py questions` still answers when it is asked. With the questions switched off, the brief asks the writing-mode question itself, as in 1.3.0.

A new setup question is a row of `QUESTIONS` in `setup_questions.py`, a row of this table and a test of each of its states.

## Later changes

The field sheet: "set the field", "change the field" or "review the field guidance" runs `python3 scripts/setup.py fields show`, then the field questions with the current answers pre-selected, then `setup.py fields set --answers <file> --dry-run` and `--yes` (with `--replace` when a sheet is there). After a pull that changed the sheet, `fields show` prints what differs and `fields approve --fingerprint <shown> --yes` records the approval once the user read it and agreed. See [fields.md](fields.md).

The deliverable can change mid-project. Run `apply` again with the new answers: it adds profiles, sections and labels and never removes what is there; for an existing hub it prints the table rows to add, for the session to add to a copy of the hub's saved body and post with `post_verified.py body --expected-body-file <saved body>`. The SessionStart brief and the `record-auditor` agent notice when files suggest a deliverable the setup does not cover (for example the first `.tex` file in a project set up only for software) and ask once whether to add it. Files present when `apply` ran, and the plugin's own workflow file, never cause that line.
