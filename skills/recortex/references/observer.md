# Optional active observation

The observer is experimental and off by default. It is one always-on note-taker of the conversation between you and the main session's agent, with several jobs: it keeps memories, a to-do list with checkmarks, the status summary and the copies of them (task lists, the board), and it drafts a change of the paper's text for you to accept. It reads what you and the agent said and the two dialogs you answered, and nothing else: your typed prompts, the agent's messages to you, the plan the agent showed in plan mode with your answer to it, and a question the agent asked with the option you chose. It reads no tool output, file contents, web page or command result, as evidence or as context, and never the plan file. From that conversation it selects the results and failures the agent reported to you, the decisions you stated in your own words or chose in a dialog, corrections, ideas, questions, the plans you agreed to, the steps the agent said are done and the items you asked to be reminded of. It records what was said; it does not judge the work itself or replace the agent's judgment. If the agent is misled, the record holds what you were told, which you saw and can correct.

Once you have chosen a level, nothing needs you in a normal session: the observer posts on its own within the level, and what it holds back for your answer the session asks you about, one multiple-choice question each (see [What waits for your answer](#what-waits-for-your-answer)). It runs only in a project folder that you enabled on this machine; repository trust alone does not enable it, and the project's shared configuration file cannot enable it anywhere. The ordinary briefs and manual recording workflow continue to work without it. A folder enabled with an earlier version (1.4.0 or before) is paused after the update: no hook captures, no worker runs and no model call is made until you answer the level question (the setup wizard's `observer-level`, or `observer.py enable --level L --yes`). The brief's setup line counts that question, and `hooks.py --doctor` and the status line say "recortex observer: paused until you choose a level."

GitHub remains the shared record. A private local queue holds work that is pending; queued, reviewed and posted are different states. A local capture receipt does not mean a result has reached GitHub. The queue is not a transcript backup: capture stores source pointers and hashes, and the native Claude transcript must still exist when a worker resolves them. Missing, changed or oversized sources defer work visibly. No lossless-session or exactly-once claim is made.

## Levels, tiers and caps

One setting, the level, per machine and project folder, kept with the observer's other settings in the private approvals file. The project file cannot set or raise it.

| Level | Runs on its own | Asks you first |
|---|---|---|
| Notes only | memories, the status summary | a held memory, as before |
| Assistant | the above, plus to-do items on an existing "To do" task, steps checked off, task lists and the hub's active list kept current, the reports | opening a task (the "To do" task too), closing a task, a held memory and every draft of the paper's text |
| Everything | all of the above, plus opening and closing tasks, the board and the sub-issue links | every draft of the paper's text, and a held memory |

At every level the paper's text is only proposed. In shadow mode nothing is posted, opened, closed or rendered at any level; reviewed events stay in the queue for the session.

Three tiers of model do the work, so that a cheap model sorts and a stronger one writes.

| Tier | Default model | What it does | Input per call |
|---|---|---|---|
| sort | `haiku` | reads each stretch of the conversation and labels what it holds, citing messages by number; it writes no record text | 32,000 characters |
| middle | `sonnet` | drafts a memory, a steps list or a mark from a label, and reviews each draft with a fresh call; refreshes the status summary | 48,000 characters |
| strong | none until you allow it, then `opus` | drafts a change of the paper's text, and reviews it with a fresh call | 120,000 characters |

Each distinct model has its own runtime check; a failed or changed check stops only its tier. A stopped sort tier stops the passes; a stopped strong tier stops only the manuscript keeper. A job that is not in your level is not drafted: a stretch whose labels all belong to jobs outside the level costs the sort call and no more.

Calls count against your Claude usage limits. The daily caps are per project, in a rolling 24 hours; the settings may lower them and never raise them (`observer.py limits [--sort N] [--middle N] [--strong N]`).

| Cap | Default |
|---|---|
| sort calls | 80 |
| middle calls | 70 |
| strong calls | 8 |
| tokens, input plus output: sort, middle, strong | 800,000, 700,000, 320,000 |
| candidates per draft | 6 |
| automatic comments | 25 a day |
| tasks opened | 3 a day |
| paper proposals | 2 a day |
| status summaries | 4 a day |
| task lists rendered by code | 30 a day |

A call is never cut short: a token budget stops the next call. A full cap leaves work queued, and the session is told once. A typical day is about 36 calls: 14 sort, 20 middle and 2 strong. These are calls, not money: no price applies under a subscription. When `ANTHROPIC_API_KEY` or a provider variable is set, the calls are billed there (see below).

## Enable and inspect

Run from the project root, using the installed skill's `scripts/` directory, in this order: enable in shadow mode with a level, check the runtime of each model, then switch to automatic mode if you want it. The setup wizard's question `observer-level` runs these steps for you (`setup.py observer --level L`, [setup.md](setup.md)); without the runtime check the observer takes notes but reviews nothing.

```bash
python3 scripts/observer.py status
python3 scripts/observer.py enable --level everything --model sonnet --sort-model haiku   # preview
python3 scripts/observer.py enable --level everything --model sonnet --sort-model haiku --yes   # 1. shadow mode
python3 scripts/observer.py runtime-check                            # 2. one check per distinct model; needs step 1
python3 scripts/observer.py enable --mode automatic --level everything --model sonnet --sort-model haiku --yes   # 3. optional
python3 scripts/observer.py pending
python3 scripts/observer.py limits --strong 4                        # lower a daily cap
python3 scripts/observer.py disable
```

`runtime-check` refuses until step 1 has recorded this folder's approval, because each check is bound to a model chosen there. Steps 1 and 3 need no terminal when the user has answered the question about them: a session's `enable --yes` (and `setup.py observer --yes`, which runs all three steps) goes through only on the one-time grant that the hook records, before the Bash call, from the user's own recorded answer to the `observer-level` question for exactly the level the chosen option names (or to the `paper-proposals` question for the stronger model, opus), and the grant holds 10 minutes and is used once, `setup.py` taking it for the whole chain. Without it the command says `enable_unanswered` and changes nothing; outside every session no grant is needed, and lowering the level, or removing the stronger model, needs none either. A level the user typed in the "Other" box, or another model, is asked in the same way: the session runs the command with it after the user's answer. The approval says where it was given, `session` or `terminal`; after a session switched automatic mode on, the next session start says so, with the date, the level and whether paper proposals (the stronger model) are on, and again whenever the level or the stronger model changes: "recortex observer: automatic mode was switched on for this folder on <date> from a session, at the level <level>, with paper proposals <on|off>; tell the session to turn it off." The acts that follow (`disable`, `release`, `resume`, `undo`) are asked as questions of their own (the table "The acts and their questions" below); they guard against mistakes and are not a security boundary (see "Task context and explicit holds").

`enable` requires `--model`, a Claude alias or model ID for the middle tier, and `--level` unless this folder's approval already holds one. `--sort-model` names the model that sorts (the middle model sorts when it is left out) and `--strong-model` the one that drafts the paper's text (the keeper stays off when it is left out; the setup question `paper-proposals` asks for it only in a project with a plan, a writing mode other than off and the level Assistant or Everything). Without `--yes` it previews the settings and says how the calls are counted: they run with `claude -p` under your Claude Code sign-in and count against your account's usage limits, at most 80 sort calls, 70 middle calls and 8 strong calls a day for the project, each tier with its own input limit. No dollar figure applies, and no saving is claimed. The calls use the environment as Claude Code does. When `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, a `CLAUDE_CODE_USE_*` provider variable or `AWS_BEARER_TOKEN_BEDROCK` is set, `enable` and `status` name it (never its value) and say that the calls are billed to that key or provider instead.

`--yes` records the settings for this project folder on this machine, in `observer-approvals.json` in the private state folder beside the user key. The entry binds the repository, the folder's real path, the exact settings and this machine's key-derived identity. Nothing is written to `.recortex.json`. A second checkout or worktree of the same repository needs its own `enable`, and a copied state folder does not carry an approval to another machine. The project file can only switch the observer off, with `"observer": false` (or an observer entry whose `"enabled"` is false); `status` then reports `project_switch: off`. That stops capture and posting, but not the holds, which stay in force while this folder has an entry on this machine. `disable` removes this folder's entry and leaves the queue and its holds; it needs your answer to the question of `acts.py ask disable`, whether or not a hold applies.

Shadow mode, the default, reviews candidates without posting. Automatic posting requires `enable --mode automatic --model M --yes` after a successful `runtime-check`, which needs this folder's approval in shadow mode first and is bound to the installed Claude executable and the chosen model. Changing a model needs a new `enable` and a new runtime check of that model. The runtime check reports `requested_model`, the model Claude announced, the credential source Claude Code named (`api_key_source`) and any billing variables, and `status` keeps them under `runtime_last`. These controls do not edit your Claude account or global settings. See the [Claude CLI model and settings flags](https://code.claude.com/docs/en/cli-reference).

The runtime check must establish structured output, disabled tools and MCP, isolated settings, and absence of hook recursion. It requires that no tool, MCP server or skill is loaded; it records, but does not limit, the plugins Claude reports. If that proof is unavailable, captures remain queued and independent model checks do not run. Merely finding `claude` or passing a unit test does not establish runtime compatibility. Verify `status`; do not describe automatic operation as active when the gate is unavailable.

Capture also requires a safe native transcript path. The transcript and its project directory must belong to the current user, and every ancestor must belong to that user or root. Symlink components and world-writable paths are refused. Group write on a folder is accepted only for the owner's private group as the local files `/etc/passwd` and `/etc/group` define it: the owner's primary group, named after the owner, with no member but the owner, and no other local account's primary group; a network account or group, a file over 4 MiB or one with any line that does not parse cleanly (a NIS `+` or `-` entry included) is refused, and the system's own lookup must agree with the files. That is the default layout on Ubuntu, where `~/.claude` and `~/.claude/projects` are mode 775. A transcript file must always be writable by the user alone, and is read through a descriptor opened without following a symlink and checked again before every read. A sticky ancestor outside the source tree is allowed when owned by root or the current user, such as a trusted shared temporary directory. A directory's owner can replace its children even with mode `0755`.

`status` reports the metadata-only `capture_preflight` check, fixed reasons such as `source-permissions`, and boundary names such as `native-config`, `native-projects` or `ancestor`. `status --source-details` additionally displays the failing directory paths, modes and ownership, without reading any transcript contents or changing permissions. Report those exact paths to the user and change nothing yourself. For a confirmed directory owned by the user that is not intentionally shared, `chmod go-w -- '/exact/reported/directory'` removes group/other write bits without changing read access, which the user may choose to do. Do not run that placeholder literally, use recursive chmod, change another owner's directory, or change shared storage merely to bypass this check. Rerun the diagnostic afterwards. A failed check leaves capture unavailable; the observer does not alter Claude's files or directory permissions.

A user namespace or execution sandbox may expose a system ancestor's owner as an unmapped identity. The observer reports `source-owner`; it does not guess that an unknown owner is root. Repeat the diagnostic where ownership can be established. Do not change ownership of system directories to satisfy the check. Offline fixtures may explicitly simulate trusted system metadata, but that simulation does not establish real capture readiness.

```bash
python3 scripts/observer.py run-worker --dry-run
python3 scripts/observer.py context --query "pipe reader" --issue 7
python3 scripts/observer.py holds
python3 scripts/observer.py pause publication
python3 scripts/observer.py resume publication
python3 scripts/observer.py discard EVENTKEY
```

Pause and resume accept `capture`, `publication`, or `all`. A capture pause keeps established holds active. A pause is yours to lift: `resume` needs your answer to the question of `acts.py ask resume`. `record --source SOURCE_ID` retries an existing queued observation through the same review path; it does not accept arbitrary model-provided file paths. `reconcile EVENTKEY --dry-run` previews receipt reconciliation. `discard EVENTKEY` drops a ready or deferred event that will not be posted; its excerpts then expire with the retention. Status and pending output distinguish local backlog, deferred evidence, budget exhaustion, uncertain publication and verified receipts.

## Shared home folders and several hosts

Many people run Claude Code where the home folder is on a network mount that every host sees (NFS, Lustre, GPFS, CephFS), and where a session starts on whatever host is free: a compute node of a batch job, a container, a cloud workspace. The observer's approval, the trusted folders and the reminders follow that case. Where a part cannot, a fixed line says so, and `hooks.py --doctor` ends with a summary of what works on this machine and why not.

An approval holds on the host where you made it, and on any host that sees the same key file: the same inode at the same real path, which a shared mount keeps for every client (the device number is never used, because a network mount gives each client its own). `observer.py status` prints `approval_reason` (empty when it holds, else one of `settings-invalid`, `unreadable`, `off`, `none`, `repo`, `folder`, `level`, `settings` or `host`) and `binding`: where the approval applies now, what it was made for (this host, a shared home folder, or any host) and a note. An approval written before 1.7.0 holds on its own host: run `setup.py observer --level L --yes` once, from any host, and it holds on every host that sees the key file. On a host where the approval does not hold, that command is a new approval there: a session needs your answer to the level question (a session cannot make an approval hold again by itself, with the stored level or any other). Copying the state folder to another machine gives a file with another inode, so a copy does not carry an approval, as before. Where the inode differs between clients (a FUSE mount that numbers files per client, such as sshfs; clients with other inode settings; a container that mounts the home at another path), ask the question of `acts.py ask hosts` and, after a yes, run `observer.py enable ... --hosts any --yes`: the approval then holds on any host that can read this state folder, a copy of it included, and `status` says so. `--hosts any` needs that answer and a subagent's call of it is denied; `setup.py observer --hosts any` is the same flag for the wizard's steps. A session start on a host where the approval does not hold says so in one fixed line.

Capture, the answers a session records for you and the usage of the plugin's subagents all read Claude Code's transcripts, and the check on their folders refuses an ancestor that another account owns or that a shared group may write, which is the usual layout of shared storage: the folder of all homes, a group's folder, the mount point. A refused answer then says `enable_answer_unreadable` (or the same for `map-mode`, `discard`, `later`, `drafts` and `act`) with the code and a note, because asking again cannot help, and `setup.py questions` does not ask the observer questions there: it prints one block with the command that asks the trust question instead. The checks only read, and the session runs them and says what they show:

```bash
python3 scripts/observer.py status --source-details    # which folders, and why
python3 scripts/acts.py ask trust                      # the question about the folders it can cover, as they are now
python3 scripts/observer.py trust-ancestor --failing --yes   # after a yes to that question
python3 scripts/observer.py trust-ancestor --list       # what is trusted, and whether each still matches
python3 scripts/observer.py trust-ancestor --forget /exact/folder   # only does less: needs no answer
```

The question names each folder with its owner, group and mode as they are now, and the label of its yes option carries a short token of those folders. This is the one question whose answer can never be read back from the transcript (it is asked because the transcript does not pass the checks), so it has a typed form: `acts.py ask trust --typed` prints it as text, the user types the words of the yes option, and the prompt hook records the grant. The grant is bound to the session that asked, is made only by a hook that Claude Code itself started, and is used only after the hook before the act has found the user's words in the transcript, or found the transcript unreadable for one of the fixed reasons.

`trust-ancestor` covers a folder that fails for its owner or its mode. When the code is another (`source-symlink`, `source-path`, `source-file`, `source-changed` and the rest), the refusal sends you to `status --source-details` only: a home reached through a link into a network mount is one such case, and the way out is to point `CLAUDE_CONFIG_DIR` at a private folder of your own on a local disk, so that Claude Code keeps its transcripts there.

A trusted folder is accepted only while its path, owner, group and mode are exactly what you trusted (the entry is kept in `trusted-ancestors.json` in the private state folder, bound to your key; one that changed is refused again and `status` says so). The transcript, its project folder and everything inside it are never accepted this way, and neither is a link or a folder that fails for another reason. Say it plainly: the owner of a trusted folder, and its group where the mode lets the group write, can put another tree in its place, and a folder that all may write with no sticky bit lets anyone on that machine do the same. The tree must still hold a project folder and a transcript that belong to you and are closed to group and others, so what can stand in is a tree of your own files, and an answer that granted once never grants again. `trust-ancestor --yes` goes only on your answer to that question (the hook refuses a subagent's call in every project), and a folder that changed since you were asked stores nothing (`trust_changed`).

Two hosts and one queue. With one approval valid on every host, two workers could run on one queue at once. The worker's own lock and SQLite rest on file locks, which reach across hosts on NFS and on Lustre mounted with `flock`, and stay on the host on Lustre `localflock` and NFS `local_lock=all`, `flock` or `posix`. A host lease is the gate in front of that lock: one small file beside it, `worker-host.lease`, made by a hard link (atomic on those file systems), with the host name, the process id, a random token and an expiry 10 minutes ahead that the worker renews at each step. A worker that finds another host's lease that has not expired (with 120 seconds of allowance for clocks that differ) leaves quietly and calls no model; `observer.py status` and `hooks.py --doctor` say "another host's observer worker holds this folder until HH:MM UTC" (with the date when it is not today's), without the host's name. Two hosts with the same host name are one host to the lease, and to an approval's `host` binding: a container given a fixed `--hostname` is the host it shares the name with, so give each its own name. A renew takes the same claim as a takeover, and the worker renews before every step that writes to GitHub (a post, the summary, a map change, each housekeeping job) and before it keeps a paper proposal; a worker whose lease ran out or was taken stops there, with the code `other-host`. An expired lease is taken over through a claim that only one worker can make; a lease that cannot be read, or that runs further ahead than a lease may (a clock far ahead wrote it), counts as held until its file's time plus the lease time plus the allowance. The lease never replaces the local lock. Where the mount keeps its locks on the host, `--doctor` says so in one fixed line: the lease keeps the worker to one host, but hooks that write on two hosts at once can still conflict, so run sessions for one project on one host at a time. A file system that makes no hard links leaves the worker its own lock and says so in `status` and `--doctor`; any other error of the mount (a stale handle, an input error, a full quota) is no decision, so that pass does not run, says so the same way, and the next one tries again.

## Capture, review and publication

Command hooks collect bounded source descriptors from the native transcript: your typed prompts, a message you type while a turn runs (which Claude Code stores as a queued command from you, with no prompt record), the form Claude Code stores a typed `/recortex` command in (for holds only), a message from a chat channel such as Telegram (for holds only: another person can write in a channel, so it never counts as your words for a decision or a change of status, nor as a source), and the text blocks of the agent's messages. Two dialogs you answered are also read, from the main session's own transcript and matched by call id: the plan the agent showed in plan mode (its text, as the `ExitPlanMode` call carries it) with your answer, approved or rejected, and a question the agent asked with the option you chose (`AskUserQuestion`). Free text typed into a dialog ("Other"), feedback typed to a rejected plan and the plan file are never read, and a question of recortex's own (a held memory, a task, a draft or a setup question) is never a source. A dialog that Claude Code does not write in a shape recortex knows (seen in version 2.1.327) is dropped and counted as `dialogs_unread` in `status`. A dialog choice is weaker than typed words: it can back a steps list and a decision in the form `Chose "..." when asked "..."`, and never a change of status. Thinking, every other tool call and result, and subagents' transcripts are not collected. The hooks make no model or network calls themselves; at session start, at a stop and before compaction a hook can start the finite worker, which does. Claude Code writes a turn's final message after its Stop hook, so that worker first waits up to about 3 seconds for the transcripts it knows to stop growing, and reads their unread parts as a hook does; the transcript stays the only source. The worker waits for about eight sources, or for one that has waited ten minutes, so that a call sees a stretch of the session. A cursor and its descriptors commit together to the private state database. A transcript seen for the first time (the observer enabled in a long session, or one resumed later) is read from its last 32 MiB; the part left out is one source gap that `status` shows. Session and subagent starts also provide local context; prompts, Bash calls, stops and compaction provide collection opportunities. No observer hook runs after other tool calls or at a subagent's stop (the separate `SubagentStop` hook of the usage count reads numbers only; see Usage below). Before a Bash call, a synchronous transcript scan checks for original user controls. See the [Claude hook contracts](https://code.claude.com/docs/en/hooks).

The hooks are registered for everyone, and cost about 3 ms each when the observer is off: `run_observer_hook.sh` looks for this folder's real path in this machine's `observer-approvals.json` and starts no Python without it. When the project file says `"observer": false` (written so in `.recortex.json`), it starts Python only before a Bash call, where the holds stay in force. When the observer is on, a Bash call costs one Python start, about 65 ms. A notice that does not change is shown once per session. Tool calls carry task context only before a git or gh action a hold can stop, and failures of the local queue are reported at the edges of a turn, not on every tool call.

The worker uses separate bounded calls. The sort call labels each stretch of the session, up to 16 messages cited by number: a memory (with its kind), a plan you agreed to, a step the agent said is done, a loose item you asked to be reminded of, or a bearing on a part of the paper's plan. It writes no record text, and its labels are only pointers. Code drops a label that breaks a rule (a to-do that cites no message you typed, a step marked from a message that is not the main agent's, a decision that cites neither your typed words nor an option you chose, a task that is not open, a plan part the record does not hold) and every label of a job outside your level; with no label left no further call is made. The draft call writes a short comment from the template for each label the cited messages support, and a fresh review call per candidate accepts or rejects it with a fixed reason. Code sets what a model need not choose: the issue of a to-do, of a new task and of a checkpoint that carries marks, and the `done=`, `dropped=`, `checks=` and `against=` values of the marker, which it composes from structured fields when the comment is posted. Models receive the conversation (who said each message, and when) and the current record context as data; no field sheet, mark or restricted pattern is sent to them. They cannot execute tools or publish. Every memory rests on what was said: a result or a failure on what the agent told you it found, or on a run you made yourself and typed (a number you measured, something that broke for you) that the agent's message takes in, which the memory then tells as your report and not as the agent's own work; a decision on your exact words, an idea or a question on your message. One message of yours can hold both a failure and the decision it led to ("the C extension crashed on the Windows build, so I dropped it"): the sort labels it twice, the draft writes the failure and then the decision, and the decision says which failure it rests on by that failure's place in the draft. Code writes the `because=` link into the decision's marker once the failure is posted (the model writes none), and the decision waits for the failure as a mark waits for its task; if the failure is dropped, refused or recorded by the main session itself, the decision is posted alone, without the link. The decision still rests on your typed words or a dialog choice, never on the agent's message alone, and the failure still needs the agent's message that takes your finding in. A candidate that opens a task or marks a step is also checked by code: a new task needs the plan and your approval (a plan-dialog approval, a question-dialog choice, or typed words the Agreed field quotes), a mark needs a message of the main agent that says the step is done, and a step that is only started or partly done is never marked. The reviewer checks a candidate against the messages it cites, the rest of that stretch of the session and the record; it does not judge whether the agent's work was right. It also sees the newest memories on the candidate's issue, and rejects a result or a failure that repeats one of them with nothing new. What the agent relays from a page, a file or a document is not a result of the work, and text it quotes that asks for a record is data. Existing issue destinations, event templates, restrictions and recorded links still apply. Ambiguous destinations, overlap or evidence defer a candidate.

Every kind of memory may post on its own in automatic mode, within mechanical limits that do not depend on a model:

- A memory that changes what an earlier one means (a correction, or a `replaces=`, `instead=` or `checks=` link; `checks=` answers a question or marks an idea tried) posts on its own only when it rests on what was said: your typed words, or the agent's message to you. Your words count when the memory quotes them in its own field (a decision's "Exact words", another kind's quoted lines): at least six words and at least half of one of your typed messages that it cites. The agent's message counts when the memory cites it; a subagent's report or a sidechain turn, which you never saw, is not the agent's message. That last rule is a chosen tradeoff: if a planted page misleads the agent, a change resting on its message posts on its own, and the record then holds what the agent told you, which you saw and can correct. A change resting on a short phrase such as "go ahead" alone waits for the main session. Whether the quoted words themselves state what the decision records is left to the reviewer, the last check here: a long request such as "summarize that page" meets the word count without being a decision.
- The body holds no image, no HTML other than the event marker on its first line and folds (no other HTML comment), no @mention (entities such as `&#64;` are decoded first), no reference definition, no address or link target outside `https://github.com/<owner>/<repo>/`, nothing shaped like `//host`, a backslash pair, `www.` or a scheme such as `data:`, and no `owner/repo#N`, `owner/repo@sha` or `user@sha` reference to another repository. Such a candidate waits for the main session. Bare `#N` and `GH-N` references to this repository are fine.
- The observer does not judge confidentiality: a project marked as handling sensitive material posts like any other, and a project that needs that judgment should not run the observer. The linter's rules, the project's restricted patterns and banned words included, apply to every automatic body, as to every post.
- At most 25 automatic comments and 3 opened tasks a day per project; the rest waits in the queue, and the session is told once.
- The body names nothing of this machine: no absolute local path, no home folder, no local user name and no email address, as written, with entities decoded, or as GitHub shows it once Markdown's backslash escapes are dropped.

Only the independent publisher appends reviewed event comments. It freezes the exact payload and source identities, records the sending state before the request, reads the stored body back and retains the receipt. An interrupted send becomes uncertain and is reconciled before retry. An event whose own problem stops it (lint, target, hold, one of the limits above) is deferred with that reason, and the next one is tried. Mutable topic bodies, the hub's text, labels and the resume block's own fields remain the main session's responsibility. The exceptions are copies that code writes from told memories, never a model (see Tasks and housekeeping), and the status summary below.

Shadow mode keeps reviewed events, with their excerpts, until they are posted by the main session, discarded, or the mode changes to automatic and they are posted.

## Tasks, steps and housekeeping

A plan you approved becomes a task: an `active` issue whose first comment is a `steps` memory with the numbered steps, and a task list under `## Plan` in its body. A step the agent reports done is checked: the observer posts a result, failure, correction or checkpoint with a `done=` mark, and code renders the box. A loose "remind me to ..." becomes one item on the standing "To do" task. The format and where the checkmarks show are in [tasks.md](tasks.md). The observer does not verify the work: a step is checked when the agent says it is done, and a step that is only started, in progress or partly done ("all tests pass except two") is never checked.

After a pass that posted something, and once a day, under the worker's lock, code does the housekeeping, each step under its own cap and recorded as an act, with no model call:

1. brings the index up to date;
2. renders every open task whose list differs from the computed one and was not changed by hand (at most 30 renders a day);
3. closes a task whose steps are all done or dropped (Everything; at Assistant it asks you first, at Notes only never);
4. renders the hub's `## Active issues` section when the hub has that heading;
5. links the tasks it opened under their topic (Everything);
6. keeps the board current when this machine has one set up (Everything).

Steps 2 to 4 need the level Assistant or higher. A step that fails records its fixed reason and the rest go on. Once a day, before step 1 and in automatic mode only, code also takes away the manuscript keeper's old working folders from this machine's private folder for the project: a draft's folder and its approved copy go once the draft is applied, dropped, stale or refused, and any such folder goes 14 days after its last change, whatever the state of its draft (a draft that still waited is then stale, since its files are gone); a folder with no draft goes after 14 days, or at once when the keeper recorded a failed attempt after the folder was last written. Only folders named as the keeper names them are looked at, nothing is followed through a link, and a folder that holds anything but the user's own files is left alone and counted. This makes no act and no call; `jobs_last` in the store keeps the number removed. A box ticked or unticked by hand on GitHub is not believed: the next render would put it back, so code does not render that task, counts it, and the brief says so; the session then asks you whether to record it or put it back.

## Optional task reminders

In a project folder with an approved observer, the user chooses how a relevant earlier decision is surfaced on a prompt. Raising the mode is a question (`acts.py ask advisory`: Deliver the reminders, Try it silently or Leave it off); `off` needs none.

```bash
python3 scripts/observer.py advisory deliver --yes
python3 scripts/observer.py advisory shadow --yes
python3 scripts/observer.py advisory off --yes
```

Choose one mode. The default is `off`. In `deliver`, an eligible reminder gives the session pointers to the standing decision and the failure it explicitly cites. This requires a complete sync within the preceding 24 hours. The bounded local lookup runs without a model call. In `shadow`, Recortex keeps a local receipt for an eligible reminder and leaves it out of the prompt. Shadow receipts and delivered receipts are separate. Use `observer.py status` to inspect them. A delivery receipt counts a pointer passed to the session. A human reviewer assesses whether it reached the user and improved the decision. These modes leave the observer's publication level and the user's holds in force.

### Review and quiet individual reminders

In the interactive local dashboard, open Observer reminders to see the task or topic and the source comments behind each issued reminder. You can mute a reminder for that context and unmute it later. When a recognized Project Map branch supplied the evidence, the preference applies within that branch. A different task or an updated evidence record can bring its own reminder. Ordinary context and recorded facts stay available.

The session can also list the same preferences, and mutes or unmutes one on your answer to the question of `acts.py ask reminder`:

```bash
python3 scripts/observer.py advisory list
python3 scripts/observer.py advisory mute REMINDER_ID
python3 scripts/observer.py advisory unmute REMINDER_ID
```

The history is private to this machine and project folder. It keeps the 100 most recent unmuted reminders and up to 100 explicit mutes. Each entry stores its timestamp, source identifiers and a reason category. Prompt text and quoted evidence stay out of this history. Shadow evaluation and delivery receipts from earlier builds have no reviewable entry.

## The reminder without the observer

The line that reminds a session of a replaced decision has its own light setting. It adds one fixed line to a prompt of the main session that names work resting on a decision the record later replaced, when no review verdict exists for that work yet: the addresses of the earlier decision, the current one and the work, and the order to read `guidance.py context` before advising. It needs what the brief hooks need (a set up, trusted project and the local index) and nothing of the observer: no level, no model, no runtime check, and notes need not be possible. It makes no model call, posts nothing, reads your prompt and the local copy of the record, and is kept per repository on this machine in `task-reminders.json`. The setup question `task-reminder` asks it; `setup.py task-reminder show` and `set --mode on|off --yes` are the setting, and no grant is needed because it takes no action and raises no level. Each item is said once a session, never for a subagent's prompt, never on a stale or partial copy, and not when the observer's own `advisory deliver` already says it. The line has a cap of its own (900 characters) and takes no room from the other lines of a prompt; checking runs under a time limit, and when it does not fit, one fixed line says so once a session and `hooks.py --doctor` keeps a note. Only text of a fixed form with addresses of the trusted repository is printed; anything else gives no line. There is no mute and no history for this light line: it ends when the work has a review verdict (`/recortex:impact`).

## The manuscript keeper

The owner's rule for the paper: text from the observer is a proposal for you to accept, never written on its own, and only when something notable changed. The keeper runs only when all of these hold: the project has a plan and a usable plan issue; this machine's writing mode is `review` or `autonomous` (off, not chosen or unreadable means nothing is drafted and no call is spent); the level is Assistant or Everything, in automatic mode with publication not paused; a strong model is set and its runtime check is valid; and something notable is due and stable.

Notable is decided by code from the index: a claim became backed since the part's newest text change; a memory the text rests on was corrected, replaced or set aside; a planned figure or table now exists (this joins a draft for the same topic, and alone only adds a line to the brief); or a claim is in doubt or the plan's message changed (a line only, never a draft). A part due only because of a new Methods decision is not notable. Stable means the part's material has been unchanged for 30 minutes, no source arrived for 10 minutes, the topic was not proposed in the last 24 hours, fewer than 2 proposals were made today and no draft for the topic waits; the keeper also leaves a topic alone for 2 hours after you started writing it from another folder.

The keeper runs `write.py start`, one strong call that drafts the whole body, a fresh strong call that reviews it, and `write.py check`, whose eight refusals are the last word. A draft that passes waits for your answer; one that fails is refused and not tried again until what it rests on changes. The worker never runs `write.py apply`. Your "Approve" is the approval, bound to the exact bytes you were shown: the recorded hashes of `draft.md`, `used.json` and `memory.json` are checked before the write, and a draft whose files changed is refused as stale. "Not now" asks again after 7 days; "Drop it" waits until what the part rests on changes. In autonomous mode the keeper's draft still waits. The way the session asks is in [writing.md](writing.md), "Drafts that wait".

## What waits for your answer

Five kinds of item wait for you. The session asks each as one multiple-choice question from a fixed template, with the options shown, and the quoted line as stored. A held memory is a change of an earlier memory's status that rests on neither your words nor the agent's message, or a memory the reviewer kept off the record (rejected as `withheld`: see "The user can also keep a session's moments off the record" below); the question of the second says so in fixed words after "It would change: ...", "(the reviewer kept it off the record, as you may have asked)". A steps memory of the second kind that would open a task is asked as a task to open. A map change is a proposal of the Project Map observer that waits for your Apply change (below, "Project Map maintenance"). A title or a plain line is record or model text: it is shown to you in the dialog and never placed in a hook payload, which carries counts and short ids only.

| Item | Question | Options | Carried out by |
|---|---|---|---|
| A held memory | `Memory <short> (<kind>) on #<issue>: "<line>". It would change: <changes>. Post it, or drop it?` | Post, Drop | `post_verified.py comment --eventkey KEY`; `observer.py discard KEY` |
| A task to open (Assistant) | `Task <short>: open a task "<title>" with <n> steps?` | Open it, Not now, Drop it | `observer.py act SHORT`; `observer.py later SHORT`; `observer.py discard KEY` |
| A task to close (Assistant) | `Task <short>: every step of #<N> is done. Close it?` | Close it, Not now | `observer.py act SHORT`; `observer.py later SHORT` |
| A map change | `Project Map <short>: <line>. Apply this change?` | Apply change, Not now, Drop it | `observer.py act SHORT`; `observer.py later SHORT`; `observer.py discard KEY` |
| A draft of the paper's text | `Draft <short>: update the <heading> of #<N>. Approve it, or not?` | Approve, Not now, Drop it | `observer.py drafts apply`, `later` or `drop ID` |

`observer.py pending --waiting [--json]` lists them with the templates filled in; the JSON form cleans the titles and lines as the text form does and carries the data header in its `data_header` field. Every answer that changes something needs a one-time grant: before the Bash call that carries it out (`act`, `later`, `discard`, `drafts apply`, `drafts later`, `drafts drop`, `post_verified.py comment --eventkey`), the hook looks in the main transcript for the question tool's own call naming that short id and quoting that line, and your recorded answer to it, with the label of that answer ("Open it", "Close it", "Apply change", "Post", "Approve", "Not now", "Drop it" or "Drop"). Only that gives a grant, kept in the private observer state for 10 minutes and consumed by the command; without it the command is refused, so a session cannot postpone or drop what waits for you on its own. An answer to another item's question, a question the session worded itself and an answer with another label give none. A tool result, a page or a subagent cannot give that answer.

At session start the observer's context holds one fixed line when anything waits ("recortex observer: N items wait for the user's answer. Load the recortex skill first, run its observer.py pending --waiting, and ask each as one multiple-choice question from the template it prints. Do not offer them in prose."). A reminder follows at the next prompts while items wait and `pending --waiting` has not run in the session, at most 3 times a session and 3 prompts apart, from the second prompt. At the level Assistant the question about a task comes with the next prompt, not at a pause.

## The acts and their questions

Every act that is the user's own is one question that `acts.py ask KIND` prints, with the command of each option. The session asks it word for word with the question tool and runs the chosen option's command; the hook records a one-time grant from the user's recorded answer to exactly that question, and the command takes it once or refuses with `<kind>_unanswered` and names the question. A label that says the act (three words or more, never a bare yes) carries a short token where a label could fit more than one thing.

| Kind | The act | Its yes label | Value the grant is bound to |
|---|---|---|---|
| `release` | lift a hold | Release hold HOLD8 | the repository and the hold |
| `disable` | switch the observer off for this folder | Turn the observer off | the folder and its approval's time |
| `resume` | lift a pause | Resume the note taking, the posting, or both | the repository, the scope and the moment of the pause |
| `undo` | reverse one act of the observer | Undo act N | the repository, the act and what it did |
| `trust` | trust folders above the transcripts | Trust these folders TOKEN | the folders' owner, group and mode |
| `hosts` | an approval for any host | Allow any host | `any` |
| `advisory` | its reminders on prompts | Deliver the reminders, Try it silently | the mode |
| `reminder` | mute or show one reminder again | Mute reminder ID8, Show reminder ID8 again | the repository, the reminder and the direction |
| `replace` | replace this folder's settings for another repository while holds apply | Replace the settings | the old and the new repository |
| `publish` | the public page | Update the public page, Set up the public page, Publish the private record | the target, the flags |

A question holds fixed words and checked values only: a repository, a hold's short id and the action it stops in words (never the text of a hold), a number, a path that trust-ancestor accepts. The question's whole text and its options in order must match for the answer to count; a reworded question, another label, a second use and a command with other values grant nothing. A newer answer that is no yes takes an unused grant of the kind away, a later pause or approval is a new question (the question names its moment), and an act done outside every session spends a grant nobody used. When the transcript cannot be read here, `acts.py ask trust --typed` is the one question that may be answered by typing the label of its yes option (see "Shared home folders and several hosts"); every other question needs the dialog, and a session without it says so in one line.

## From a terminal

The commands still run from the user's own terminal, outside every Claude Code session, with no question: where the act needs a word (`release`, `disable` while a hold applies, `resume`, `undo`) the command asks for it there, as it always did. A session never tells the user to do this; it asks the question. The plugin tells a terminal from a session by `on_terminal()`, never by whether /dev/tty can be opened.

## The acts log and undo

Everything the observer does beyond posting a memory is an act in its private store: a memory posted, a task opened, steps added or marked, a list rendered, a task closed, the hub's list rendered, a status summary, a board update, a draft proposed or applied. `observer.py log [--days N]` prints each act with its address. At session start, at most once in 6 hours per session, one notice built from fixed words and numbers says what it did since the last one ("recortex observer: since <stamp> it posted 6 memories, checked 3 steps, opened 1 task and closed task #14. observer.py log lists them."). The mind page's to-do view ends with the acts of the last 7 days.

If the log cannot take the act of something the observer did (a post, a draft of the paper's text, a render), what it did stands and the failure is counted: `observer.py status` shows `acts_failed` (the count) and `acts_failed_day`, `hooks.py --doctor` prints one line with the count and the day of the last failure, and at session start, at most once a day while it keeps failing, one fixed notice says so ("recortex observer: the log of what it did could not be written N time(s); run hooks.py --doctor."). A failure more than 7 days old is no longer told, and the count then starts again.

`observer.py undo ACT`, which goes on your answer to the question of `acts.py ask undo` (it names the act and what it does on GitHub), reopens a closed task, restores a rendered body from its backup (refusing a body that changed since), or closes a task it opened as not planned. For any other kind it prints one fixed line that says how that kind is corrected: a memory by a correction, a change of the text by `versions.py restore`. When it writes nothing it says why in one fixed line beside its code: `changed_since` (a later act or someone else changed the body, which includes a read of GitHub that still shows the body from before a newer act), `no_backup`, `failed` (GitHub or the check before the write refused it), `not_closed`, `not_open`, `already_undone` or `no_such_act`.

## The main session's own memories

While the observer is on, the main session still posts its own memories with `post_verified.py comment` (and `create_issues.py`), in shadow and automatic mode. Each verified post is registered in the observer's queue, so that nothing is posted twice: the observer drops its own candidates of the same kind for the same issue that rest on what came before that post, and its ready events of that kind for that issue wait for the main session. The sort call also leaves out a moment that an agent message in the same stretch says it has just recorded, with the address of its comment, so that no draft is paid for it. A copy of a queued memory (its reviewed body, with or without its event key), a decision the queue already holds with the same exact words, and a change of status of the same memory (the same `replaces=`, `instead=` or `checks=` target) as a held event still waiting are refused with the event key: post that event with `--eventkey`, which keeps its holds and the session's withhold. Discarding an event posts nothing and does not lift this: a copy of a discarded event is not posted, and a discarded decision that was held (by a hold, the session's withhold, or the automatic gate; the queue marks it so for good) still blocks its exact words. The whole queue is searched, by digest; when the search cannot complete, the post is refused. A memory the session rewrites in its own words still posts. Two paths are the main session's own work and stay open: discarding a held event and then writing its own change of status, and a correction that names the memory only by its address.

To post a reviewed event, in automatic mode, use `observer.py pending` to find it and `observer.py pending --eventkey KEY --show-body` to display its reviewed body, then `post_verified.py comment --issue N --kind <kind> --body-file <that body> --eventkey KEY`. The issue, kind and draft must match the event exactly; the script uses the shared publisher and receipt, so retrying a verified event does not append another comment. The main session may post a deferred event this way after its own review, and the daily cap of automatic comments is not its. An event the automatic gate held back for your answer (a change of status that rests on neither your words nor the agent's message, or a memory the reviewer rejected as `withheld`) is listed by `observer.py pending --held` (and, with the other items that wait, by `pending --waiting`); at the next session start, where the hook says how many items wait, the session asks you one multiple-choice question per memory, from a fixed template that names its short id, its kind and what it would change and quotes its plain line (or, for a body without one, its kind and the start of its first paragraph), with the options "Post" and "Drop", then posts it this way or drops it with `observer.py discard`. There is no terminal step, but the post is bound to your answer: before the Bash call that runs `post_verified.py --eventkey KEY`, the hook looks in the main transcript, read as capture reads it, for the question tool's own call in a main-session message naming that short id and quoting that line, so that you answered about that memory and not a description the session wrote, and the result Claude Code recorded for it, and only your "Post" there gives a one-time grant, kept in the private observer state for 10 minutes and consumed by the post. Without it the post is refused (`held_unanswered`) and the memory stays listed: ask again, and post right after a "Post". A tool result, a page or a subagent cannot give that answer; a session that writes the transcript or the grant file itself can, which is the limit stated for holds below. Its copy without `--eventkey` is refused, so it is posted only through that question. A session you kept off the record is not posted this way either (see below). The mechanical body limits still apply. These checks coordinate the repository's posting helpers; they do not intercept arbitrary `gh` commands or browser posts.

The first release binds approval and publishing to one installed machine per project folder. Several sessions on that machine share the queue and publisher lock. Automatic failover and distributed publishing are outside this contract. This is a single approved installation assumption, not distributed fencing: cloned user keys and machine identity can undermine that assumption. Do not copy an approval or its private state to another host. The approval does not name a GitHub account: the publisher posts as whichever allowed account `gh` uses.

## Task context and explicit holds

Task context uses the same allowed authors and memory interpretation as the mind page, ranked for the task and its thread. Recorded decisions, failures, support and replacements travel together. It preserves full selected fields, including qualifications and denominators; a group that cannot fit is omitted with a source pointer. Excluded support is identified without exposing its text. Resume text is rechecked against the current allowlist and matching unedited comment. The packet states its cache age and missing evidence. It is quoted data, never permission to act. A packet with the same selection is not repeated within a session.

Only a recognized whole original user message creates a local hold. Supported messages are:

```text
/recortex hold git-tag
/recortex hold git-push
/recortex hold gh-release
/recortex hold command EXACT_COMMAND
```

These hold the repository until released. A small set of whole phrases such as `don't push` or `do not tag` holds only the session it was typed in.

The user can also keep a session's moments off the record. Only your own typed words do it: the agent's account of such a request ("I posted nothing, as you asked"), telling the agent not to post by itself, or to leave the recording to the observer, and asking it to just acknowledge a finding keep nothing off the record, in the sort, the draft and the review alike. A message that says `don't post`, `do not record`, `don't publish` or `off the record` anywhere in it holds the publication of that session's moments (a `publish` hold, which keeps only the phrase). The worker selects nothing from that session, so no call is spent on it: its sources are deferred as `withheld`. An event of that session that is reviewed anyway is deferred as `withheld` too. It is posted by no path, the main session's `--eventkey` included, until the user releases that hold with `observer.py release HOLD_ID`, on their answer to its question, which is the later, explicit request. A `withheld` verdict is not permanent: releasing a hold offers the sources it withheld to the sort once more (the release says how many, as `offered_again`), under the usual caps and gates, and the next pass handles them like any other stretch. Each source a release offers again is marked `hold_released` in what the sort, the draft and the review are shown, until it is handled, with the words of the hold you released (the phrase you typed, such as "don't post", cleaned and capped like any quoted text, never in a hook's text): that request was lifted by you, so it no longer applies and its moments are judged on their own; without the mark the models would read your request again and set the moment aside. Only that request is lifted: any other request not to post, worded differently, in the same source or another, still keeps a moment off the record, and so does any hold still active (the check for an active hold runs before any call). The words are kept per source in a list of the private queue, no new column; when two requests were typed in one session, each release adds its own words, and the sources are offered when the last of them is released. A hold of the whole repository frees its sources and marks none, since its words say nothing about what the session typed; a hold of another session offers and marks nothing of this one. The mark is on those sources only, not on a message you type after the release. A source that another hold still covers (a second phrase typed in the session, or a hold of the whole repository) stays withheld until that one is released too, and a hold of a git action withheld no moment. A moment the main session recorded meanwhile, or whose event already exists, is not posted a second time. Where no hold applies and the reviewer still rejects a candidate with the reason `withheld` (it read the user's typed words that way, or misread them), the candidate is not dropped: it waits as a held memory, "What waits for your answer" above, for your Post or Drop. A hold of the session that is still active blocks even a Post, until you release it. The hold stops no command. The hook interprets the persisted original message, typed as plain text or in the form Claude Code stores for a typed `/recortex` command. Arbitrary natural language is not a policy parser. "Original user" means the user role in the transcript: in a session driven by the Agent SDK or `claude -p`, the host's message has that role, so a host that relays outside text can set a hold; a hold only denies.

Nothing in a session releases a hold by itself: not a typed message, not a transcript line, nor a hook's input. A hold is the user's stop, and the session asks to lift one only when the user says so. `release`, `disable`, `resume`, `undo`, `trust-ancestor --yes`, `advisory` and `enable --hosts any` each go only on the one-time grant that the hook records from the user's answer to the plugin's own question about it (`acts.py ask KIND`), and refuse without it with a code `<kind>_unanswered` that names the question; an `enable --yes` that replaces this folder's entry with one for another repository while the holds of the one it names apply is the same (`replace`), and when those holds cannot be read it is refused with `holds_unreadable` and a fixed line. A subagent's call of any of them is denied. `"observer": false` in the project file switches the observer off but leaves its holds in force. To release one, the session runs `python3 scripts/acts.py ask release HOLD_ID`, asks the question it prints (the hold named by its short id and the action it stops, in fixed words, never the text of the hold), and runs `observer.py release HOLD_ID` on a yes (`observer.py holds` lists the ids). Compaction, elapsed time or omission from a summary releases nothing. Holds, pauses and these confirmations are guards against mistakes, not a security boundary: they stop the model's direct commands, but a program run with your rights can still change your private files, reach `observer.py` under another name or delete the queue file, which lifts every hold. Do not rely on them against a session that is trying to get round them. A session with shell access can still find a way around them: your answers in a dialog are the real gates, and the checks exist to stop accidental actions. A hook refuses a Bash call that names `observer.py`, `setup.py`, `publish.py` or `acts.py` together with a program that makes a terminal (`script`, `unbuffer`, `expect`, `socat`, `faketty`, `pty`), but another way to get a terminal is not recognized. The user's own terminal is told from a session's by `on_terminal()`: outside every Claude Code session (neither `CLAUDECODE` in the environment nor a `claude` program among the parents), whatever terminal a command has. It chooses the typed word for `release`, `disable`, `resume` and `undo`, never whether /dev/tty can be opened. A hook of the plugin is never run by a session (the guard denies `hooks.py` and `run_hook.sh` but for `--doctor` and `--print`), nor another Claude Code session started to answer for the user. This is the accepted limit: a session with shell access can still get around these checks, and the real gates are your answers in a dialog (each one-time and bound to the answer's own id) and your own terminal. The holds that apply are those of the repository this folder's entry on this machine names, whatever the project file says; when the approvals cannot be read, the check fails closed as for unreadable holds.

The local check can deny Bash calls for Git push, Git tag changes, GitHub release changes, and an exact command string. It looks at every simple command of the line: it splits on `;`, `&&`, `||`, `|`, `&` and newlines, leaves out redirections, leading variable assignments, shell keywords such as `if` and `do`, and wrappers such as `env`, `sudo` and `timeout`, and looks inside `bash -c` and `sh -c` strings, `eval`, `watch` and every `find -exec` group; `xargs git` and `xargs gh` count as every held action of that program, since their arguments come from stdin. Then a general rule: a simple command whose own words include all of a held action's words (`git` and `push`, `git` and `tag`, `gh` and `release`) is that action, whatever program starts it (`retry git push`), unless it is that action's read-only form run as the command's own program, its flag an option before any `--` (`git push --dry-run`, `git tag -l`, `gh release view`; `env git push --dry-run` is held). A line with ANSI-C or locale quoting (`$'...'`, `$"..."`) is not decoded: every held action counts as present. The words inside one quoted argument are one word, so `echo 'git push'` and a quoted commit message run; `git log --grep push` is held. A line it does not take apart (an unbalanced quote, a command or process substitution, a here-document, a subshell) is denied when it holds the held action's words, such as `git` and `push`. A wrong denial is accepted: you asked for the hold. `git -C <path>` counts as this repository, and a `gh` command whose `--repo` names another repository is not this repository's. Read-only commands such as `git status` and `git push --dry-run` go on. Shell aliases, scripts, programs run by other programs and other tools are outside the check. It does not enforce a universal shell policy. Ordinary context and advice never deny a tool, and an asynchronous warning cannot stop a completed action. The holds are read before each Bash call without the queue's locks. When they cannot be read at all, in a folder where the observer is on, every Bash command is denied with one fixed reason except `pwd`, `ls` and `cat` with plain path arguments and no option: the options of other reading programs can run another program, and git obeys the repository's config. The reason tells the session to run `observer.py status` by its full path with python3 and nothing else on the line, and to tell the user what it says: that command and `hooks.py --doctor` are the two that pass then; it names no way round the check. Whether a command typed at Claude Code's prompt with `!` passes through this hook is not established here, so the reason does not rely on it.

UserPromptSubmit can run before its transcript line is written and can represent an initiated turn rather than a person. Hook prompt text alone therefore cannot prove user authority. The check before a Bash call rescans persisted original sources; if those sources lag, a new hold may not yet be enforceable and a fixed warning says so. Check the acknowledged hold with `holds` before relying on enforcement. Existing Claude permissions remain in force.

Recognized explicit control quotes are a narrow local-storage exception: they are stored without model review so local enforcement can work, after mechanical secret and restricted-pattern checks. They are not sent to a model for classification. Narrative source text is not archived by capture. Independent review may retain the minimum evidence needed by a candidate; the reviewer must reject unnecessary sensitive text. Pattern checks and framing are limited defenses, not proof that arbitrary text is harmless.

## The status summary

The observer also keeps the project's status summary current, so that a session that never ends has one. In automatic mode, when the summary is stale by the brief's own rule (5 or more told memories since the newest resume block, or a day since it with at least one) and publication is not paused, the worker makes one more model call that writes only the "In short" paragraphs (two, at most 1,200 characters) from the index's told memories, the plan's integers and the recent typed prompts and agent messages it holds, a fresh call that reviews them (supported, no number the sources do not give, no secret, no address or issue number), and, only when both passed, posts a new resume block through `resume_block.py update` with the stamp "by the observer". Code writes the rest of the block from the index: the active issues with their step counts ("#14, 3 of 5 steps"), the next open step of up to 5 open tasks, and the 3 newest told decisions; the current focus and the holds are copied from the newest block word for word. At most 4 a day; both calls are counted in the middle tier's cap as the job `status`; a session the user kept off the record is left out of the sources; the hook shows no reminder while this is on. In shadow mode, or with publication paused, nothing is posted and the hook's reminder shows.

## Usage

What the plugin used is measured in tokens and calls, never money; under a subscription these count against your usage limits and no price applies.

- The observer's own background calls are exact: every call's tier, model, job (`sort`, `memories`, `status`, `paper`, `check`) and its input, output, cache-read and cache-write tokens are kept in the private store, which is also the ledger of the daily caps. Token columns are zeroed after 35 days.
- The plugin's own subagents (`recortex:record-auditor`, `record-drafter`, `record-reviewer`, `record-planner`, `record-planner-session` and `ask`) are exact for what their own transcript holds. A `SubagentStop` hook adds the four token counts and the model name to `usage.db` when one stops; it prints nothing, returns no context and runs under a 5 second limit.
- What the hooks add to your sessions' context is estimated: characters divided by 4, per event.
- The main session's own work on the record is not measured.

`usage.py show [--days 7|30] [--json]` prints the numbers in the terminal, and the mind page's last view, "What did recortex use?", shows them: today against each tier's caps, the last 7 and 30 days by tier and job, a bar for each day, the largest users of the week and the plugin's subagents. `usage.db` holds only integers, a tier, a job, an agent name from the fixed list, a model name and a day; rows older than 35 days are removed by the observer's daily cleanup. Expect about the same use as 1.4.0 (8 percent less by one weighting, 9 percent more by another): the gain is what gets recorded, not the cost.

## What you should still expect to do

The observer sees what is said in the chat, and nothing else.

- Work done away from the session (a run on a cluster, a figure made by hand, a call with a coauthor) is not seen. Say it in the chat, or record it.
- A result the agent found and never stated is not seen. The session still states outcomes with their numbers, and its own recording stays in place; nothing is posted twice.
- A step is checked when the agent says it is done. The observer does not verify the work.
- It does not judge confidentiality; a project that needs that judgment should not run it.
- Numbers are kept as said. Evidence lines, figure blocks and Sources rows that need a file or a commit are the session's, as are bodies outside the plan, plan revisions and the author's questions.
- Answer what waits: drafts in review mode, held memories, tasks to open or close, boxes and cards changed by hand.
- Glance at the acts line. A wrong task or checkmark is one command to undo.

## Limits and recovery

Defaults are 80 sort calls, 70 middle calls and 8 strong calls per project in a rolling 24-hour window, with token budgets of 800,000, 700,000 and 320,000 (the table under Levels, tiers and caps), including failed calls, at most 32,000, 48,000 and 120,000 input characters per call by tier, six candidates per draft and 25 automatic comments a day. A failed sort or draft call is tried again after five minutes; a failed batch is offered again in halves, and a source that fails on its own stops after three attempts and stays in `pending`. The settings may lower those ceilings, never raise them. A full call cap or token budget leaves pending work queued and says so once. The default backlog cap is 128 MiB or 10,000 pending observations. Reaching a cap stops accepting new capture without advancing its cursor and leaves a persistent degraded status. Pending evidence is never silently expired.

The pending database lives under the private state directory, separate from the rebuildable index in the cache directory. It uses synchronous SQLite transactions, private permissions and checked paths. It must not be deleted as a cache repair. Corruption is reported; it is not silently reset. Reviewed excerpts of handled events become eligible for cleanup after seven days by default, configurable to a shorter interval; pending evidence is never silently expired. A finite worker checks cleanup daily while the plugin is active, including when capture is paused or the model runtime is unavailable. This is not a wall-clock retention daemon. Identity metadata, explicit holds and publication receipts remain, as do observation metadata (transcript paths, offsets and hashes), invocation times and hold quotes, all private with mode 0600. Native Claude transcript retention is managed by Claude, independently of this queue.

After interruption, inspect `status` and `pending`, restore source availability where possible, and reconcile uncertain sends before retrying. A verified receipt establishes the stored comment matched the frozen draft at read-back; it does not establish that the underlying research claim is true. Local queued work still needs review and publication before another machine can recover it from GitHub.

## Project Map maintenance

The Project Map follows the project's ideas, components and methods across sessions. Its durable history is on the project hub. On an approved Assistant or Everything observer, `observer.py map-mode shadow --yes` tries it in this folder; the setup question `map-upkeep` asks it, and a session may run the command once on your recorded answer to that exact question (the plugin's own question, the option's label, used once; lowering or switching it off needs none). Read the private results with `observer.py map-proposals`. Each entry shows the proposed change, whether it qualified for automatic publication, links to cited records, and the dates and roles of the supporting messages. Structural proposals list each affected branch by ID with its title and parent before and after the operation. Shadow proposals stay local when you switch modes.

Choose `observer.py map-mode automatic --yes` (on your answer "Automatic (Recommended)") to allow maintenance in automatic observer mode. The observer considers recent eligible conversation, standing project memories, and headings in files approved during map setup. A separate reviewer checks the proposed operation. An unattended addition requires both typed user evidence and a matching trusted record. An unattended rename also requires typed evidence linking the old and new names. The two middle-tier calls share the existing daily call and token limits. No model runs for the map while its mode is off.

Moves, splits, merges, deletions, restorations, and uncertain changes appear under `observer.py pending --waiting` for a decision. A deletion proposal preserves the children. A removed branch can be proposed for restoration only after new work. The proposal waits for the answer to its exact question. A changed branch requires a new preview. To stop maintenance, choose `observer.py map-mode off --yes`.

When you return to a distinct branch, task context can bring back the standing records that branch cites. A stale snapshot or ambiguous branch name uses ordinary retrieval. Task-time suggestions follow the separate advisory setting.
