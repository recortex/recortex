# The mind page

> Commands on this page write `scripts/<name>` for short. That is the `scripts` folder of this skill, next to `SKILL.md`; call it by its full path.

The mind page is one local file that tells a project's memory in sentences: what was thought, tried, decided and learned, and how one memory led to the next. It is built from the local index alone and read by a person in a browser. It is not a list of issues, it never changes the record, and the session never reads it.

## Project Map

Every dashboard has a **Project Map** tab next to **Overview**, including on a phone or in an empty project. Open it directly at `#project-map`. Expand a branch to see its children. Selecting its name shows its description, evidence, related branches, and recent changes. The search matches branch names and descriptions. Open a decision from the evidence list and use Back to return to the same branch. Branch addresses survive renaming and moving. The full nested outline also works without JavaScript.

Start an empty map in chat with `/recortex:map`: the whole first tree is one `seed` change and one comment on the hub, however many branches it has (up to 200; a longer first map is seeded in part and added to). Each branch has an `id` of your choice so that children can name their parent, a title, and optional description, evidence and links; the preview shows every branch with its parent and evidence, and one `apply` posts them. A seed is only for a map with no branch, by a user, never by the observer; its history line reads "Started the map with 15 branches". A collaborator on 1.6.0 does not know `seed`: it skips that comment, and every later change that names a seeded branch, so their page shows an empty or partial map until they update (update before seeding). In a local interactive dashboard, **Edit project map** previews the affected branches before you apply a correction. The standalone page shows the last synced and verified map. A manuscript appears as a branch only in projects that include it.

## Open your dashboard

In Claude Code, type `/recortex:dashboard` or say "open my dashboard". It builds the page from this project's local record and gives you its address. Manuscript projects with a reading view also get a direct manuscript link. When Claude Code runs on another machine, copy the printed HTML file privately to the device where you want to read it.

To refresh the local record first and open the page from a terminal, run these scripts from the project folder.

```bash
python3 scripts/index.py sync
python3 scripts/mind.py --open
```

`--figures` also fetches the pictures of figures that are not yet kept (see "Figures as pictures"); `--sync` does too. `--versions` (and `--sync`) first bring the versions of the text that the record vouches for into the private cache (`versions.py fetch`), so that the History of each part can show what changed; without either the page uses what is cached and contacts nothing ([versions.md](versions.md)).

`mind.py` runs from the project folder like every script and prints the `config: ... repo: ...` line first. It builds the page from the index as it is; `--sync` runs `index.py sync` first, and without it nothing contacts the network. It prints `wrote <path> (N KB): M memories in T threads`, a line when anything is not told, and `open it in a browser: <file address>`. `--open` asks the browser to open that address and says whether one could be started; the address is printed either way.

It builds nothing, prints one line and exits 1 when:

| Case | Line |
|---|---|
| The repository is not in your trusted list | `mind: this repository is not in your trusted list, so no page is built. The page tells only the memories of accounts you allow.` |
| There is no local index | `mind: there is no local index of this repository; run index.py sync` |
| The index may not be read (another owner, loose permissions, not this plugin's) | `mind: the local index cannot be read; run hooks.py --doctor` |
| An older version of the plugin wrote the index last | `the index was last written by an older version of the plugin, or never by this one; run index.py sync` |

An earlier page is then left as it is. A page built while the last sync was unfinished says so in its last lines. `index.py query mind` prints the same counts in one line (`--json` prints the whole model the page is made from, for tests and for a person at a terminal).

## Put the page on the web

The page can be public, for people who have no access to the machine. That is the user's decision, and it is one question: the session runs `python3 scripts/acts.py ask publish`, asks what it prints word for word, and runs the command of the option the user chose. The question names the repository, the target (a repository, a branch and a file), what anyone with the address can read, and, in fixed sentences, what the first publish makes: a branch that holds only the page (one commit with no parent, and an empty `.nojekyll`), and GitHub Pages switched on for that branch, which makes the branch a public website. A private record has its own label and a sentence that says PRIVATE. The question reads GitHub to set those flags (`--create-branch`, `--pages`, `--private-record`, `--no-site`); `publish.py` holds GitHub's answers against them again at the send, and stops when the record is private or the branch is missing and the question that was answered did not say so. A user who wants another place says so, and the session asks again with `--to`, `--branch` and `--path`. Where the account may not write, or the target cannot be read, the script prints one fixed line and no question.

```bash
python3 scripts/acts.py ask publish --to octo-org/octo-pages --branch gh-pages
python3 scripts/publish.py --to octo-org/octo-pages --branch gh-pages --dry-run
python3 scripts/publish.py --list
```

`publish.py` builds the static page itself (the same steps as `mind.py`, with none of this machine's usage numbers, no log of the observer and nothing interactive; it takes no path of a page, so it cannot be pointed at another file). It stops, sending nothing, when the page is not the static one, holds text that the project's rules keep off the record (a secret or a restricted pattern), found in the record's own text before any page is made from it, in the page's text (read with and without the line breaks between elements, so that a word split by markup is whole again) and in every attribute of the page, when a hold of yours stops publishing, when your account may not write to the target, or when the page is larger than 25 MB. It then prints what will be public and sends one commit of one file through GitHub's contents API with the message "Publish the project dashboard page" (or, for a branch it makes, one commit with no parent through GitHub's git data calls), reads the file back and compares its hash, and keeps the newest 20 receipts on this machine (`--list`); a receipt says whether the record was private, so that the next question can say it without asking GitHub. It prints "the page: ADDRESS" only when GitHub Pages serves this branch from its root and the address has the expected form, and "GitHub may take a minute to show the new version."; otherwise the file's address on GitHub, and, when no site is on, a line that setting the public page up gets one. A refusal to switch Pages on is one fixed line and never a failed publish. `--dry-run` and `--list` read and send nothing and need no answer. To take the page down, delete the file from the branch; copies that others made stay. A site published from a private repository can still be public. The page is never committed, copied to a branch or sent by hand: the guard stops a command that names `mind.html` together with `git`, `gh`, `curl`, `scp`, `rsync`, `sftp` or `wget`, because that skips the privacy check.

## On a machine with no browser

`mind.py --open` writes the page and asks the browser to open it. On a machine where none can open (on Linux, none of `DISPLAY`, `WAYLAND_DISPLAY` and `BROWSER` is set, or the browser says no), it prints no address and none of the lines about views: the session's whole reply is "The dashboard is ready; this machine has no browser." and one question, to set up (or, after the first publish, to update) the public page and get its link, or to show the file's path. Where a page was published from this machine before, the question is the publish question for that target, so the one answer is the grant for it. For the paper (`mind.py --paper --open`) the reply is "The paper is ready; this machine has no browser." and the file's path. The live dashboard below is started there too, and `dashboard_action.py open` gives its link and then this question; its actions also work in the chat (`/recortex:todo`, `/recortex:impact` and `/recortex:map`).

## The live dashboard

The dashboard is a page that follows the record. A small server, started by the session start, serves it on this machine at `127.0.0.1` only: one server for every project of the user on that host, behind an address prefix and two keys that are new each time it starts. It stops 24 hours after the last session that used it, or when you choose Stop on a page. The page asks the server every 5 seconds whether the record changed and reloads when it did (not while a dialog is open or you are typing in a field). The "Projects" link opens a list of every project the server knows.

`python3 scripts/dashboard_action.py open` (`/recortex:dashboard`) opens the browser. Two links exist. The view-only link is the one a session may be told: with it nothing can be changed, and its buttons copy a request into the chat. The link with changes on reaches you in the line recortex shows above the session's reply (the hook's `systemMessage`, which the model does not read), in a private launch file that opens your browser, and in your own shell. `link` prints the view-only link; `status` says whether the server runs; `stop` ends it.

The server starts on every machine, and the link is offered everywhere. Where nothing shows that your browser reaches the machine (a remote machine reached over SSH outside VS Code, or a machine with no browser), `open` gives the link first and then asks the one question of the section above: put the page on the web, or show the file's path. recortex never asks you to set up a port forward. To switch it off, set `"live_dashboard": false` in the plugin's `settings.json`, or `RECORTEX_DASHBOARD` to `off`; `hooks.py --doctor` says whether it runs.

## Record a completed task step

The live dashboard's Work view reports a task step complete. Open it with `dashboard_action.py open` from the configured project folder.

A session that runs `open` gets the view-only link and never the one with changes on; the page's own confirmation is what makes a change. The server stops 24 hours after the last session, or when you choose Stop on any of its pages; its address stops working then. Choose one unfinished step, enter what you completed, review the exact checkpoint, and confirm. The record identifies it as your completion report from the dashboard. Recording checks GitHub again and can take about half a minute: the page says so at once, turns its buttons off, and then shows the receipt, or one line that says it failed and points to the receipt check. A verified receipt links to the posted checkpoint. If updating the task list or rebuilding the snapshot fails afterwards, refresh the display. Use the operation history to check a pending receipt. When the existing observer is enabled at the Everything level, finishing the final step can make the task eligible for closure.

## The ways in

These views remain available inside the project areas. Existing bookmarks open the corresponding view or individual memory.

| Destination | What you can find |
|---|---|
| Project Map | Browse the nested hierarchy, switch between the visual branch map and a compact outline, and open the evidence for a branch. |
| Overview | The recorded focus, next actions, owners and holds. Open the original status or expand its summary. A missing or withheld status has its own explanation. |
| Work → Tasks | Open tasks and steps. A completed step cites its checkpoint. Task history includes recently closed work. |
| Work → Open questions and limits | Open questions, untested ideas, failures with no recorded follow-up, and limitations on current findings. |
| History → Timeline | Additions by posting time or events by event time. Filter by topic, kind, state, words and date range. |
| History → Current understanding | Standing decisions, findings and corrections with their replacements, supporting stories and topic text. |
| History → Topic stories | Choose from all project topics, ordered by the latest included posting. Each story follows the work from its first record and links to any related output text. |
| History → Lessons, Memory maps | See failures and their consequences, or explore links across threads. |
| Outputs → Current text and sources | Current deliverable text in section order, with its origin, last change and related work. A topic can contribute to multiple deliverables. |
| Outputs → Read the manuscript | A supported manuscript's text, plan and available versions. [Manuscript reading and revision tools](#the-manuscript) |
| Search memories | Match words in the included project memories or use a preset question. |
| Recortex usage | Recorded calls and tokens for the observer and the plugin's subagents. |

"How to read this page" in the side bar opens a box that explains what a memory, a thread, a part and a pause are, and every kind and state. Every kind word and every state is a button that opens its own fixed explanation: the page never shows a state without saying what it means. The words are fixed wording of `mind.py`; no record text is in them.

Any sentence opens its memory in a side panel. A project word carries a dotted underline: pointing at it shows its meaning, choosing it opens a box with the meaning, why it matters, the longer story, the parts of the text and the memories that use it. A cited issue shows as words, never as a number. Every pointer, such as a thread name, a section or "the rest is on GitHub", is a link.

### What the states mean

| State | Meaning |
|---|---|
| Still stands | Nothing recorded later replaces a decision, finding or correction or sets it aside. It is what we hold today; it can still turn out wrong |
| Replaced, Set aside | A later memory of the same kind says something else; or we chose not to go this way and a later memory says what we did instead |
| Still open, Answered | A question that no later result, failure or decision answers; one that one does |
| Not tested yet, Taken up, Tried | An idea nothing took up and no result tested; one that a later decision or finding was made because of (no result has put the idea itself to a test); one that a result or a failure tested |
| Nothing followed yet, Led to a change | A failure that no decision or fix points back to; one that a later memory was made because of |
| A pause | Where a stretch of work ended and a note was left for whoever came next. It is not a claim, so it has no state; what came after it follows by time |

A thread is "N open points" when it has open questions, untested ideas or failures nothing followed, and "Nothing open" otherwise; its text can still change. The record keeps one current version of each part. It is not marked draft or final, and no status is added to the record: the page shows the day each part last changed and what was recorded in its thread after that.

### How the text is drawn

The text of a topic is read as structure and drawn from it: paragraphs, headings of the text's own (`###` to `######`), nested lists, numbered lists, quotations, code blocks, bold and italic, superscripts and subscripts, pipe tables and HTML tables, and the figure and table blocks where the author put them. An HTML table is read with its rows, cells, header cells, `rowspan` and `colspan`, `align` and the inline tags `b`, `strong`, `i`, `em`, `code`, `sup`, `sub`; every other tag and attribute is dropped and its text kept, the text of `script` and `style` is dropped, and a table in a table, a table over 40 rows or 12 columns or one the reader cannot take becomes one sentence and a link. Any other HTML stays text exactly as written. A link `[words](address)` is drawn as a link only when its address is an issue, pull request, comment or file of GitHub; any other address is written out as text beside its words.

Formulas are converted when the page is built, by a small converter in `scripts/mind_text.py`, to MathML, which current browsers draw themselves. The subset is common LaTeX: letters, numbers, `+ - = < > / ( ) [ ] | , . ; : ! * '`, Greek letters, the operators and relations `\sim \le \ge \ne \pm \times \cdot \approx \to \infty \partial \in \propto \ldots`, `\sum \prod \int` with limits, named functions (`\log \ln \exp \sin \cos \tan \max \min \lim \Pr \Var \Cov`), `_` and `^` with one token or one group, `\frac`, `\sqrt`, `\hat \bar \tilde \dot \vec \overline`, `\left` and `\right` with `( ) [ ] |`, `\mathrm`, `\operatorname`, `\text`, `\mathcal`, `\mathbf`, `\mathbb`, the spaces `\, \: \; \! \quad \qquad`, and the escapes `\% \{ \} \& \# \_ \$`. A formula of more than 400 characters inline (2,000 in a display), more than 8 levels of groups or 300 nodes, or one that uses anything else (environments, `\href`, `\def`, colors, alignment with `&`) is shown as the source as written, inside a block of its own, with the line "A formula the page cannot draw is shown as it was written." The look of a drawn formula depends on the math font the reader's system has; with none, it is still correct and legible. Nothing is loaded to draw it.

The text of a memory's plain line is one sentence and is not parsed. The text, its sub-headings, tables and formulas are shown in full: a part is cut only past 40,000 characters, and then it ends with a link to read the rest on GitHub.

`index.py query mind --json` prints the model the page is made from. Its shape follows the version of the plugin: it is a view for tests and for a person at a terminal, and no script reads it.

The page places memories before or after a pause, and puts them in order, by the instant each stamp names. A marker's offset gives it; a stamp with a zone abbreviation that `zones.py` knows (PST, PDT, CET, UTC+2 and the like) is converted by that abbreviation's own offset; a stamp whose zone is not known is placed by the time GitHub gave its comment. The days the page writes ("On November 14") stay the days as written in the record. The scripts write their own stamps in the zone the record states (the `timezone` entry of the project file, as `setup.py` wrote it from the hub's convention line), and in UTC when it states none that `zones.py` knows.

## The plan and the changes of the text

For a project that has a plan (`.recortex.json` has `plans`, [planning.md](planning.md)) the page tells the paper's plan beside its text; for any other project none of this appears and the page is what it was.

- **The plan against the text**, at the top of "What does the manuscript say?": the paper's message as a sentence, then one row per section with how many parts are planned for it, how many are backed, how many have a finding against them or rest on something that changed, and whether the section has text. Each section is a link to its text.
- **What we plan to say here**, under each section heading that has planned parts: one row per part, three cells (the part, its evidence, its text), each a sentence. The part's sentence opens its comment on GitHub; "Agreed on November 16" or "Added by the session" says who stands behind it. The evidence cell says "Backed by 2 findings", "A finding speaks against it (November 20). 1 finding for it" and so on, each linked to the finding it names. The text cell says "In the text since October 21", "In the text since October 21, before that finding" or "Not in the text yet". A figure or table whose claims are backed and whose block does not exist shows "Can be made now": the plugin never makes a figure.
- **A part's status line** gains sentences: "4 planned parts belong here: 2 backed, 2 not backed yet."; "Last changed on October 21, 2026, by the plugin with your approval. See what changed."; and "You changed it by hand after that." when the body is not the text the newest change says it left.
- **History**, a fold after each part that has changed: every version, newest first, with its day, how it came about in fixed words (written by the plugin without asking, with your approval, approved by you on GitHub, edited by you by hand, restored by you), the reason, and the names it carries. How to go back to a version is said once at the top, in fixed words: ask in the chat. The page changes nothing itself. With versions kept ([versions.md](versions.md)) each version also shows what changed, drawn on the page; with the writing mode off or not chosen, the fold lists only the days the body changed, from the edit history the index holds.
- **What is still open?** gains three groups: planned claims nothing backs yet (with the experiment we thought of), planned claims a finding speaks against, and findings the plan does not use.
- A finding that carries `checks=` or `against=` to a planned part says "This bore out a planned claim." or "This spoke against a planned claim." on its card; a change of the text is a card of its own ("We changed the text to say that ..."), with the hashes and the version it holds left out; the plan issue has its own story, "The plan of the paper"; and the map of what we know gets a branch "We plan to say (4)" under a section.

With versions kept ([versions.md](versions.md)) the History fold also draws what changed in each version, and above the parts "Versions of the paper" lists the named versions with the author's words and what changed since the name before. The page links to no commit, branch or tag. A version's text is drawn only after its file's SHA-256 matched the "after" value of the told text change that names it; otherwise the entry says "The text of this version could not be checked, so it is not shown." The removed and added words of a difference are the page's `del` and `ins` elements, made by one function from the model's runs, as text.

The states of a part are the table in [issue-model.md](issue-model.md), "The plan of the deliverable"; the page computes none of them: the model (`mind_plan.py`) takes them from `plan_rules.py` and the page draws what the model says. A planned statement is record text: it is text on the page and never markup, an attribute or an address, and it is told only under the rules below, like a memory.

## The manuscript

A project whose profiles include a shipped profile with a plan (today the manuscript profile) has a view under Outputs, "Read the manuscript" (the profile's noun: "the thesis", "the report"), the third after "Where are we?" and the text view. It shows the paper as a paper: a sheet at most 1,060 pixels wide with the text in the deliverable's order and a quiet margin beside each part and each paragraph. It shows that profile's sections only, and its title is "The manuscript" with the project's name under it (no command sets a title, and the hub's title is not one). Every other project gets the page it had. The text view keeps the plan against the text, "What we plan to say here", "Versions of the paper", each part's status line and "Why it says this"; in its place of the print button it says "Read it as a paper". A part's History is drawn once, in the manuscript view: the text view's part says in one fixed line that the history is in "Read the manuscript" and links to that part's box (the link opens it). With no plan issue the view is the text with its figures, tables and sources and nothing else: no marks, slots, authorship or switch.

- **The bar** stays at the top while the paper is read (a bar with no list of versions does not stay: it is read once). It holds the two ways to show it, a line that says which text is shown, the buttons "Previous change" and "Next change" (round arrows with those words as their titles at 1,180 pixels and below, and "Change 2 of 4" or "No later change" said after each jump), the way back to "The plan and the text" and "Print or save as PDF" (below 1,180 pixels the print button is under the title instead). With the script, the ways are a radio group: "Changes since", beside a list of versions, and "Clean copy"; choosing a version in the clean copy shows the changes. The page is built in "Changes since" with the previous version chosen; without the script it stays as built. The part a link or a key jumps to lands under the bar, and the side bar lists the sections, marks the one being read and scrolls on its own on a short window. "What the marks mean" is one wrapping row under the plan message.
- **Versions** are numbered, 1 to N, one for each told text change with a kept commit (a restore counts), in time order. The list offers the ten most recent earlier versions, newest first, and the twenty newest of the older versions that carry a name (a fixed line says how many named ones were left out), each as "Version N · day", with "(previous)" on the one before the newest and the name in quotes when the record names it. A name is drawn only when it is one that `versions.py name` would accept. The current text is compared with the chosen version. With one kept version, with none, with the writing mode off, or when no part could be compared, the list is not drawn and one fixed line says why, in the line of the bar. A named version stays a label: the page never presumes that a version was sent anywhere.
- **What a version marks.** A reworded paragraph shows the words that changed, joined into phrases (added words underlined, removed words struck through); an added paragraph and a changed table, list or figure get a bar; a paragraph that is gone is one quiet line with its words in a fold. A paragraph with a formula, a superscript or a subscript on either side, or with another run that is more than plain words that the two sides do not share (code, a link's target, a citation, emphasis), is a changed paragraph, shown as it was, and never a reworded one, so that no formula is drawn as its source, no superscript or subscript is drawn flat and no structural change is erased. A changed table of the same shape washes the cells that differ, and a screen reader hears "(was 3 of 4)" there; a table of another shape is shown as it was. The margin says "Reworded since version 4", "Added since version 4" or "Changed since version 4", and the line in the bar counts them: "2 changes in 1 part since version 4, November 17", then, only when they apply, "; 6 parts have no earlier version to compare" and "; 2 parts are not compared" (and "Nothing changed since version 4, November 17, in the parts compared" in place of "Nothing changed" when some part could not be compared). The comparison of paragraphs is bounded: past a budget of pairs, or for a paragraph of more than 1,500 words, or past a total of 2,000,000 places that one comparison walks, the rest are told as removed and added, or as one changed block. Choosing another version shows that version's marks; the page reads the choice, never the address, and keeps nothing: a reload returns to the previous version. Each earlier text of a part is compared once. The marked variants of all versions share a budget of 2 MB; past it the oldest versions are left out of the list and a fixed line says so.
- **A part against a version** is in one of these states, said in its margin: same (also proved by the hash of the live body when no file is kept), marked, new since (the version's text had no such heading), "has not been fetched yet" (its file is not in the cache: build with `mind.py --versions`; the view says how many parts and the terminal says it once), "could not be checked" (the file has another hash, and none of its text is drawn), "has no kept version at or before" the chosen one (said once, in the line of the bar, not by each part), and long (past 40,000 characters: drawn without marks). The text of an earlier version is read only from the private cache, and only after its SHA-256 matched the "after" value of the told change that names it; nothing is fetched when the page is viewed.
- **The margin of a part** says its states in fixed words, each with its count, in a group that wraps: "2 planned parts backed", "A finding speaks against 1 planned part" (with a link to the finding), "1 planned part rests on something that changed", "1 planned part: nothing backs it yet", "1 planned part can be made now", "1 planned part can be written now", "1 open question", "2 failures nothing followed"; each state word that has an explanation opens it. A part with more than two states shows the first, which is the most important (a finding against it, what rests on something that changed, what is planned and not backed, what can be made now, what is backed, then what is open and what failed), and folds the others into its note as "4 more states": the fold is built open, so that without the script the note is as it was, and the script shuts it, so that a note stays about eight lines tall at the margin's width. Then how the part stands against the chosen version, and one line with when it last changed and how, "History (N)" and "How we got here". History opens a box under the part with every version headed "Version N · day" (and its name in quotes), how it came about and what changed, and for each version its own request for the chat ("Restore the Results of November 17 at 19:40, the version changed by you by hand.") with a button, named by that time, that copies it; Escape closes the box that holds the focus. The notes of the margin sit beside their rows, and a note that is taller than its row is moved down by the script so that it never leaves a hole in the text. The box takes focus when it opens, and the page keeps it shut at the start only through the script.
- **Who wrote a paragraph** is told from the versions kept on this machine, only when versions are kept: the origin of a paragraph is the oldest version of the unbroken run, counted back from the newest, that holds an equal paragraph. "Written by the plugin, without asking" (or "with your approval", "approved by you on GitHub"), "Restored at your request", "You edited it by hand", "Your own words, edited by hand on (day); the plugin keeps them as you wrote them" (a later change of the plugin to the part left it as it is), "You changed it by hand since the last kept version" (the newest kept version does not hold it) and "In the text since before versions were kept". Consecutive paragraphs with one origin share one note. The walk stops at the first version whose file is not kept or not checked, and the paragraphs still in the run there get no note. The paper's authors live on the versions branch, not in the index, and are not told.
- **What the plan says that the text does not yet**: under the last part that its topic names, a list "Planned for the Results and not in the text yet" of dashed boxes, each with a line like "Planned table · nothing backs it yet" ("Planned · nothing backs it yet" when the plan's own words start with the kind) and the plan's own words, in the plan's order, at most 12 in a section and then "and N more in the plan". A part that can be written now offers a button that copies "Write this part of the Results: planned part 9302." (the id of its plan comment; the plan's own line is never in the copied request, and the session reads the part with `index.py query plan`). A section with no text shows "No text yet", what is planned and backed, and, when the plugin may write it, the request "Draft the Discussion from what is backed." with its button. The slots show in "Changes since" and when no version can be compared, never in "Clean copy" or in print; a part or a section with no text is left out of the print.
- **Figures and tables** are drawn as a paper draws them, numbered by the style: a figure with its picture (when the build kept it) or a frame with the fixed line "The picture is not in this page: it was not kept on this machine when the page was built." and the link, then its caption and where the picture is; a table in a box that scrolls on its own, which a keyboard reaches and a screen reader names by its number ("Table 2"), the table itself by its caption. A figure or table that an earlier text had and the current one does not is drawn from that text's own entry, and its picture is embedded when the build kept it. "Where the numbers come from" closes the sheet.
- **Print** always prints the clean current text: one heading and date line ("As the record says on November 17, 2026"), a page break before each section, parts with their titles and numbers, figures, tables and equations kept whole, and none of the side bar, bar, margin, marks, slots, history, plan message, the plugin's notes under a figure or table ("The picture is ...", "Made from ...") or the closing line. A figure whose picture is missing prints "[Figure 1 is not embedded in this copy]". The foot of the sheet says that `mind.py --paper` writes the paper as a page of its own. The print style sets the light colors whatever the screen shows, which also fixes the dark theme's print of the other views and of `paper.html`.

`mind.py --paper` is as it was: the exact paper of a named version, vouched live against the decision, the tag, `VERSION.json` and every file by hash, in that version's own layout, written as `paper.html`. Its title is the view's: "The manuscript" (the profile's noun) with the project's name under it, and a part is titled by its text's own first heading, as the view titles it, never by the title of its issue (a part with no heading of its own has its issue's title). In a project with several profiles it holds the manuscript profile's sections only; a project with no plan keeps the hub's title and every section. Its headings and numbering are those of the view's print. The view's own comparison is of the current text with a version kept in the cache; it is not that check.

## Who is told

The page speaks as "we", so it tells only what your allowed accounts wrote: the repository's owner and the logins listed for it in your trusted list.

| Text | Told when | Otherwise |
|---|---|---|
| A memory, with its fields, links and folds | An allowed account wrote it and either it was never edited, or every edit was made by an allowed account (its edit history was read) | Not told; its links do not count and its folds explain nothing. Counted in the last lines. A memory told after edits carries a quiet note when opened |
| A planned part, a change of the text | It is a memory of an allowed account that was never edited, or edited only by allowed accounts (as any memory); a plan issue that another account opened is not used | Not told; it backs nothing, agrees nothing and links nothing |
| A word's meaning, what a thread is about | The memory that holds it is told | Not used |
| "You changed it by hand after that", the figure and table blocks a planned part names | The topic's body is told (the row below) | Not said; the part is not judged against a body nobody can vouch for |
| The text of a topic (its name line, sections, tables, formulas, figures, sources), and the order of the deliverable's sections from the hub's table | An allowed account opened the issue, its edit history has been read, and every edit was made by an allowed account | One sentence and the thread's address; the thread is named after its `topic:` label |
| The last pause | The resume block the sync checked (allowed author, never edited), when its comment is still one the page may tell | "No pause has been recorded yet", or one sentence that says to sync |
| Another issue's title | An allowed account opened it, its history is read, and nobody else renamed it | "an issue someone else opened"; the box gives who, when, open or closed and the address |
| Another issue's first lines, an open task's goal | As the text of a topic | Not shown |
| An account name | It has the form of a GitHub login | "an account" |

The last lines of the page count what is not told and why: memories by accounts outside your allowed list, memories changed on GitHub after they were posted (each with "Open it on GitHub"), older memories beyond the 2,000 newest (`compile.py` writes the whole timeline), and comments of a kind this version of the plugin does not know. They show in full under "Where are we?"; every other way in ends with one line that counts them and links there. A set-aside thread is named after its closed topic's title under the title rule, and after its label otherwise; a task's title is told under the same rule.

## Edited memories

A posted memory is never edited; a correction is a new memory. A memory whose comment GitHub says was changed after it was posted (its `updated_at` differs from its `created_at`) is checked: the sync reads, from GitHub, who made each edit. Only such memories are read, never all of them.

- Every edit was made by one of your allowed accounts: the memory is told as before, and its opened view says "Changed on GitHub after it was posted." The note also shows in `index.py query mind --json` (`changed`) and in `query recall` (a short mark after the line). Its links count, its folds explain, and the linter accepts a link to it.
- Any edit was made by an account outside your allowed list, or by an account that no longer exists, or the edit history has not been read (yet), is not whole, or is older than the comment's last change: the memory is not told, its links do not count and its folds explain nothing. `query recall` says how many it left out, the last lines of the page count them with "Open it on GitHub", and the linter refuses a link to it (`link-target`). A history that cannot be read counts as an edit by someone outside.
- A comment that looks changed but whose history shows no edit (a reaction, a stale answer) is not told either: nothing proves it is the text that was posted.

The allowed list is applied when the index is read, so adding a login to your trusted list tells that login's edits at once, with no new sync. Resume comments are not memories: an edited one stays ignored, whoever edited it. When the repository is not in your trusted list, every account counts and so does every edit.

An edit made in the same second as the post is not seen. It leaves the two times equal, and only comments whose two times differ are read, to keep the sync's cost small; such a memory is told as if it was never edited, whoever made the edit. This gap is small (`post_verified.py` reads each comment back right after posting), and it was already there before histories were read.

Every page of an edit history is read, for memories and for the text of a topic, 100 entries at a time. A history of more than 5,000 entries is not read to its end and counts as an edit by someone unknown, so that text is not shown.

## In short

"Resume work" opens with the newest "In short": the first field of the newest resume block that an allowed account posted and nobody edited, as two short paragraphs of text, marked "As of" the day the block says it was written. A block from before 1.3.0 has none, and a record with no usable block says so in one fixed line, "No summary of where the project stands has been written yet. The next resume block carries one."; the rest of the view is as it was. The summary is text and never markup, an attribute or an address.

## Printing the paper, and the paper as a page of its own

In a project with a plan the manuscript view ([The manuscript](#the-manuscript)) has the "Print or save as PDF" button; in any other project the text view has it. It asks the browser to print. The page's own print style leaves the paper alone on the sheet: no side bar, no tour, no folds (History, "Why it says this", the plan against the text, the versions), a page break before each section, and figures, tables and equations kept whole. The browser's print dialog offers "Save as PDF". The style holds no record text, so there is no running header; the browser adds the page number.

`mind.py --paper` writes the paper alone as `paper.html`, beside `mind.html` in the private folder, and prints its address; `mind.py --paper --version NAME` writes `paper-NAME.html`, the paper as of a named version. It makes no mind page and needs no model: it takes each told topic's text for each section in the deliverable's order (the sections a named version had, from its own `VERSION.json`), with its figures, tables and formulas, and "Where the numbers come from" at the end. A named version is written only when the record vouches for it (the decision, the tag, `VERSION.json` and every topic file by hash, as `compile.py --version` checks), else one fixed line and nothing is written. The page is built by the same builder under the same Content-Security-Policy and the same rules as the mind page; its title, part titles, sections and numbers are those of the manuscript view's print ("The manuscript" with the project's name under it, each part titled by its text's own heading, the manuscript profile's sections only); its one fixed script (`page/paper.js`) only asks the browser to print. Pictures are embedded only after `--sync` or `--figures` fetched them. The page of a private repository holds private text: do not copy it anywhere shared. For a journal's format, the Manubot-format files on the versions branch stay ([versions.md](versions.md)).

## What the session does

When you ask to see or open the project's memory, the session runs `index.py sync`, then `mind.py --open`, and gives you the address. It does not read `mind.html`: to answer a question about the history it uses `index.py query recall`, `query timeline` and the issues.

## How the page is kept inert

The file is self-contained: one style and one script, both fixed files of the plugin allowed by their hashes in a Content-Security-Policy that loads nothing else (no fonts, frames or connections, and pictures only as `data:` addresses of figures that the build embedded). Record text is only ever text in the page, never markup, an attribute or an address; every link out is an address on GitHub that the page built from checked parts. Every element is made by one function from a list of names and attributes; the list holds the inline elements the text needs (`h4` to `h6`, `pre`, `i`, `sup`, `sub`) and fifteen MathML elements, which only the formula builder makes, from a tree it checks again (the element names, text only inside tokens, the number of children each name takes, at most 300 nodes and 8 levels; a tree that breaks a rule is shown as its source). The manuscript view adds `figure`, `figcaption`, `fieldset`, `legend`, `label`, `select` and `option`. The attributes `rowspan`, `colspan`, `start`, `display`, `mathvariant`, `accent`, `aria-expanded`, `aria-controls`, `data-explain`, `data-fold`, `data-mode` (`changes`, `clean` or `plain`), `data-for`, `data-added`, `data-reworded` and `data-changed` (whole version numbers only; `data-for` also marks a changed cell of a table), `data-toggle` (a name the page made), `data-copy` (`1`), `scope` (`col`), `title` (only "Previous change" and "Next change", on the bar's two buttons), `checked`, `selected`, `value`, `open` and `preserveAspectRatio` (`none`) are accepted only on the elements and with the values listed in `mind.py`. The script routes by place, opens fixed explanations, folds branches, shows the marks of the version the reader chose and copies a request; it holds no record text (a button copies the words of the element before it, and a version number is read as a whole number before it is used), keeps nothing in the browser and puts nothing in the address. It also lays the notes of the margin out beside their rows (one `ResizeObserver` on the text, the choice of a version and of a mode): it measures them and moves a note down with its own style, and never touches the text. The brand icon above the project's name is a third fixed file, `page/icon.txt`: two lines of path data that the build refuses unless they hold only `M`, `C`, `Z`, digits, spaces, commas and minus signs. It is drawn as an inline `svg` of the page, not loaded as a picture. The usage view and the to-do view add no element and no attribute to those lists. The meters and the bars are `svg` rectangles whose sizes the page computes from whole numbers it checked (a number that is not a whole number from 0 to 1,000,000,000 is 0), with no inline style; the words of the usage view are fixed words of `mind.py` plus a day or a time of a fixed form, a model name of the form `[A-Za-z0-9_.:-]{1,100}` and those numbers, and a value outside that is dropped. Step texts, task titles and the plain lines of memories are text children only, never an attribute; a task title that someone outside your allowed accounts changed is not shown. The tables of the usage view are scrollable regions that a keyboard reaches, as the manuscript's are.

An allowed account can still write a misleading plain line; the fields and the original comment are one step away.

## If the browser says it cannot open the file

A browser installed as a snap (Firefox on Ubuntu, by default) may not read files under hidden folders in your home folder, such as `~/.cache`, and answers "Access to the file was denied". Open the address in a browser that can read it, such as Chrome, or one installed from a package rather than a snap.
