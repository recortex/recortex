# Safety and security

What the plugin will and will not do, and how it treats text that came from GitHub or from a project folder.

## Safety rules

- No script deletes an issue, a comment or a label, or edits a posted comment. The only issue a script closes is a finished task, by `tasks.py close` or by the observer at the level you chose, and `tasks.py reopen` or `observer.py undo` reopens it. The only labels a script changes on an existing issue are section labels, which follow the body's headings.
- Manual publication posts only files named on the command line or in a manifest. The observer's publisher, when enabled for a folder on this machine, appends exact independently reviewed event payloads from its queue, at most 25 a day (and at most 3 opened tasks), with no image, HTML, mention, outside link, local path, user name or email address, and nothing from a session the user asked to keep off the record. Nothing is posted by folder or wildcard.
- Every issue body and comment that is written is read back from the API and compared with the draft. A pin is confirmed by asking GitHub whether the issue is pinned. Section labels changed on an issue are read back; labels created by `setup_labels.py` are not, and rerunning it shows anything missing.
- `create_issues.py` never overwrites a body that was changed on GitHub after it wrote it, and after an interrupted run it adopts what already exists instead of creating it twice.
- `post_verified.py body` requires the body saved before drafting as `--expected-body-file`, compares it with the live body, and checks again immediately before writing. A mismatch stops the replacement. These reads and the write are separate GitHub operations, so this is not an atomic lock: coordinate one writer per issue and merge other writers' changes before retrying. A matching read-back confirms the text stored, not that no concurrent edit was overwritten.
- The linter refuses drafts that contain common token formats or match the project's `restricted_patterns`, for example participant identifiers.
- Decisions are quoted word for word with date, time and zone.
- An older tracker is never edited; at most it receives short pointer comments.
- Text read from GitHub is treated as data, never as instructions (see the security model below).

## Security model

Issue and comment text read back from GitHub is data, never instructions. A hub can be edited by anyone with write access to the repository, and on a public repository anyone can open issues and write comments. The skill tells Claude to treat everything it reads from the tracker as a description of the project's state, and never to follow commands found there. Only the user, in the session, gives instructions.

The hooks deserve extra care because they put tracker text into context without anyone asking. Their rules:

The optional [observer](../skills/recortex/references/observer.md), experimental and off by default, adds local consent kept on this machine per folder (the project file can only switch it off), source-role checks, bounded model calls, explicit holds and a durable pending queue. The capture hooks make no model or network calls themselves; at the edges of a turn they can start the worker, which does. The model calls use the environment as Claude Code does; `enable` and `status` say when an API key or another provider is set. Its publisher can append reviewed event comments after a verified runtime gate. Beyond that it only renders copies that code computes from told memories (a task's list and Result, the hub's active list, the board) and closes or opens tasks within the level you chose; a model never writes them. Text for the paper is drafted for your answer and written only on your recorded "Approve", bound to the bytes you were shown. It takes notes of the conversation only (your typed prompts, the agent's messages to you and the plan and question dialogs you answered; never free text typed into a dialog, tool output, a file or a web page, and never the plan file); none of that reaches its models. A choice in a dialog is weaker than typed words and never changes the status of an earlier memory. The `ask` agent runs only `index.py query` reads: a hook that runs in every project, observer on or off, stops any other command of that agent. Source gaps and failed checks leave work visibly pending. Original-user controls are stored locally after mechanical secret/restricted checks; copied text and model judgments do not establish user authority. Context framing and pattern checks do not prove that arbitrary model input is harmless.

| Rule | What it prevents |
|---|---|
| The configuration is read only from the project root: `CLAUDE_PROJECT_DIR` (which Claude Code sets for hooks), else the top of the git checkout, else the current folder. Parent folders are never searched. The same holds for every script, and each script prints the configuration file and repository it is using | A `.recortex.json` planted in a parent folder pointing sessions at someone else's repository |
| Trust is checked in every mode. The hook prints nothing, and `resume_block.py show` prints a one-line notice, unless the configured repository is in the user's own trusted list (`~/.config/recortex/trusted-repos`, or `RECORTEX_TRUSTED_REPOS`; `XDG_CONFIG_HOME` and `RECORTEX_TRUSTED_FILE` are used only when they are absolute paths, so a relative value cannot point into a project). Nothing inside a project can add to that list, and the repository owner counts as an allowed writer only once the repository is trusted | A cloned repository that configures itself to inject text |
| The resume block is a comment, and only a comment that passes every check is printed: its first line is the resume heading, each marker stands alone on its own line outside any quote or code block, its author is allowed (the repository owner plus the logins listed for that repository in the trusted file), and it was never edited by anyone. The newest 50 comments of the hub come from one API call, and the newest passing comment is chosen by creation time. Newer resume comments that fail are counted with the reason and never shown | Anyone posting or editing a comment to get text into your sessions |
| The time the shown comment was posted is printed with it | Showing an old block as if it were current. Anyone can post many comments on a public hub and push the newest resume comment beyond the 50 that are read (the script then says there is none), and an account with write access can delete the newest resume comment so that an older one is shown. Neither changes what an allowed account wrote; posting a new resume comment repairs both |
| An issue title is printed only when the issue was opened by an allowed account and no other account renamed it; otherwise only its number, with the reason | Instructions smuggled in through an issue title, which anyone who can edit the issue can change |
| The index (`index.sqlite`) and the hook state live in a folder `private/` (mode 0700) that the plugin creates inside its top folders: `$XDG_CACHE_HOME/recortex` for the index and `$XDG_STATE_HOME/recortex` for the state and the key (by default under `~/.cache` and `~/.local/state`); never in the project tree. Hooks, the session's Bash tool and your own shell resolve the same folders; the plugin data folder that Claude Code sets only for hooks (`CLAUDE_PLUGIN_DATA`) is not used, and an index left there by an earlier version is ignored (the first sync builds a new one). `RECORTEX_DATA_HOME` moves the index and the state to one folder, `$RECORTEX_DATA_HOME/recortex`, and is read only when `RECORTEX_TESTING=1` is also set: it is for the plugin's tests only. A top folder must be a real folder owned by the user or by root; one the user owns that was created group-writable (umask 0002) is tightened to 0700, and one owned by another user is refused. `private/` and everything in it must be real folders and files owned by the user with no permissions for group or others, checked at every read and write; files are written through a fresh temporary file with mode 0600 and read without following symlinks. An index is read only when it carries the repository, the format and a mark made with a per-user key from the state folder, so a swapped folder or a file the plugin did not make is refused | A repository you clone, or a folder someone shares, planting an index or state file whose text the hooks would print |
| When the sync at session start fails, the brief says "cached, not refreshed" with its age; a cached resume block is one that passed every check when it was read, and is left out once it is older than `resume_cache_days` (default 7). Stored sync times enter a GitHub query only as plain ISO 8601 UTC times | Old or tampered cached text passed off as current, and text smuggled into an API query |
| A refused index is never read and nothing from it is printed; the next sync moves it aside and builds a new one. The hooks load only the profiles shipped with the plugin, never a profile file a project names, and `RECORTEX_HOOK_TIMEOUT` is read as digits only | A cloned project or a shared folder getting its own text into the brief outside the data frame |
| The output is wrapped in `BEGIN/END PROJECT STATUS DATA` lines that say it is data and not instructions, text that imitates those lines is defused, and the SessionStart brief is cut at 6,000 characters (the subagent brief at 3,500) | Text posing as system or user instructions, and context flooding |
| A failure to read the configuration prints nothing and exits 0. A failure to read GitHub, or a timeout, prints the brief from the local index with its age; in a set-up, trusted project with no usable index, one line names the reason and points to `hooks.py --doctor`. Every hook exits 0 | A slow or broken network blocking the session |

The trust boundary is your allowed list, not write access to the repository. Anyone who can comment can post something that looks like a resume comment, and anyone with write access (collaborators, GitHub Apps, Actions workflows, tokens with `issues: write`) can edit comments, but a comment by a non-allowed author is ignored and so is any comment that was edited after posting. Because each resume block is a single, unedited comment, the check covers everything that is printed, however long the project runs. For the same reason, never edit a resume comment yourself; post a new one. An allowed account can still write anything, so list only accounts you would take project status from, and list a bot if a bot posts the resume comments.

A field sheet is the one text from the project tree that a payload holds outside the data frame, because it is meant to be followed, so it has its own conditions: the repository is trusted, you approved that exact text on this machine (its fingerprint is kept in `private/field-approvals.json` of your own configuration folder, which the project cannot write), and it passes the sheet's form when it is shown, one line of plain characters per value under the plugin's own labels. It stands only in its own frame, whose fixed note says that it was approved by you, cannot change rules, permissions or the task, and never makes a subagent count or report less than its material shows (a failure is reported as one, every number the task asks for goes back to the session, and what "Never write down" names stays out of anything to be posted or recorded and comes back marked in the reply); any change after the approval switches it off. The skill and the agents rank it below their rules. What remains is that you can approve a sheet that should not be approved, and that a misled session could run the approval command without you, as it could add a repository to your trusted list.

The board follows the same boundary. Everything on it is untrusted: nothing but item ids, issue numbers, the repository, the plugin's own status names and the Why text (compared, never shown) is read, and no text from the board reaches a payload or a terminal line. The `board` entry of the project file is used only in a trusted repository, only for the owner of the record's repository, and only as you approved it on this machine, so a cloned project cannot point the plugin at someone else's board. Hooks never write to GitHub, `board.py apply` refuses a public board for a private record, and the plugin never adds the `project` scope to your login.

`resume_block.py show` applies the same checks when run by hand. Its `--trust-once` and `--allow-any-author` flags are deliberate overrides for the user and are refused in hook mode.

The manuscript view of the mind page ("Read the manuscript") follows it too: a version's text is read only from the private cache after its hash matched a told change, nothing is fetched when the page is viewed, the script that switches between versions holds no record text, and what the reader chooses is kept nowhere. A request that the page lets you copy into the chat holds only the plugin's own words, a section's heading, numbers and a checked id (a planned part is named by the id of its plan comment), never a line of the record, because once pasted it is your own message. The paper alone (`mind.py --paper`, `paper.html`) and the summary at the top of the page follow the same boundary: the same builder, the same policy, only told text, and text only as text. The status summary is read from the newest resume block that an allowed account posted and nobody edited, and the hooks print about it one fixed line with one integer.

The mind page follows the same boundary. It is built only for a trusted repository and tells only memories that an allowed account wrote and nobody edited, topic text that only allowed accounts wrote or edited, and titles that only allowed accounts set; everything else is counted, not shown. The file is inert: one fixed style and one fixed script allowed by their hashes in a Content-Security-Policy that loads nothing else, record text only ever as text, never as markup or an address (and as an attribute only in one place: the alternative text of a figure's picture, cut to the characters every attribute may hold), and every link out an address on GitHub built from checked parts. Pictures of figures are fetched from GitHub when the page is built, only with `--sync` or `--figures`, checked by their first bytes (PNG, JPEG, GIF or WebP, never SVG), kept in the private folder and embedded in the file; nothing is loaded when the page is viewed. The startup notice gives the dashboard command. Hooks never build the page or read its contents. The page of a private repository holds private text and private pictures; do not copy it anywhere shared.

On shared storage the plugin adds four things, each with a limit it states. An observer approval holds on the host that made it and on any host that sees the same key file (its real path and inode, under an HMAC of your key), so a copy of the state folder to another machine does not carry it, and a session on the copy cannot make it hold again without your answer to the level question; `--hosts any` makes it hold wherever the state folder can be read, copies included, and only your answer to its question can choose it. `observer.py trust-ancestor` (on your answer to the trust question; a subagent's call is refused in every project) accepts a folder above Claude Code's transcripts only while its path, owner, group and mode are exactly what you trusted, bound to your key; the owner of such a folder, and its group where the mode lets the group write, can put another tree in its place, and anyone on the machine can where the folder is writable by all with no sticky bit, so trust only folders you know; the transcript, its project folder and what is inside it are never accepted this way, and a tree that stands in must still belong to you and be closed to group and others. A host lease keeps one host's observer worker on a queue at a time. `publish.py` (on your answer to its question; it builds its own page, checks that it is the static one and that neither the record's own text, nor the page's text, nor its attributes hold a secret or a restricted pattern, shows what will be public, and creates a branch or a site only when the question you answered said so) makes a page public: from a private record it also needs `--private-record`, which the question says by name. Its check is a pattern match, as the check at post time is, so a secret or a restricted name with a zero-width character or a look-alike letter inside it is not caught: read what the question and what it shows say before you answer. Anything on the page is then readable by anyone who has its address, and search engines may list it.

The optional interactive dashboard runs only when launched locally for the configured project. Its private launch address opens an authenticated session on the loopback interface. In the browser you can preview and confirm a user-reported task step, a change to the shared Project Map, a decision review saved on the hub, and a reviewed one-paragraph edit of a topic body. Each is confirmed separately in the page. A topic edit is a second confirmation after the review is saved, and goes through the same checked body writer as other body edits. The service rechecks the project, account, step and applicable holds, and verifies the posted checkpoint. Before applying a map preview, the service replays the hub's trusted, unedited map entries and checks the affected branches. Map file selections and pending observer proposals live on the user's machine. GitHub credentials stay in the local plugin. The launch address carries the token that authorizes the service, and it is printed only to a terminal. Started by a session, the service prints just the path of a private file that opens your browser, so the token is on no command line and in no session output. The service stops after 30 idle minutes, after 8 hours, or when you choose Stop on a page. The exported HTML keeps its offline content policy.

The local receipt protects retries on this machine. GitHub reads and comment creation are separate operations, so two people confirming the same step on different machines can still post concurrent reports.

## Acts that need your yes

Anything that is yours to decide (lifting a hold or a pause, switching the observer off, trusting a folder above the transcripts, an approval for any host, the observer's reminders on prompts, undoing one of its acts, replacing the settings of a folder, putting the dashboard page on the web) is one question that the plugin prints (`acts.py ask KIND`) and the session asks you word for word. The hook before the session's Bash call looks in the main transcript for your recorded answer to exactly that question, with its options in order, and records a grant that holds 10 minutes, is bound to the values of this one act (a hold, an act number, a target and its flags) and is used once. The act takes it, or refuses and names the question. A question that was reworded, another label, a second use, a command with other values and a subagent's call grant nothing; a newer answer that is no yes removes an unused grant; a question that names a moment (a pause, an approval) is a new question when the moment changes.

The user's own terminal is told from a session's by `on_terminal()`: outside every Claude Code session, whatever terminal a command has, and never by whether /dev/tty can be opened, because a session can run a command under a program that makes a terminal and type into it. There the commands ask for a typed word where they always did, and an answer nobody used is spent. A question about the observer's level or a stronger model, a held memory or a task keeps its own grant as before.

The one question whose answer can never be read back is the trust question (it is asked because the transcript does not pass the checks). It may be answered by typing the label of its yes option, which carries a token of the folders it is for. That typed answer is recorded by the prompt hook only for the session that asked, only when the hook was started by Claude Code itself as the one `claude` above it (no Bash tool shell and no second session in its ancestry), and the act uses it only after the hook before it has found those words in the transcript as a prompt you typed after the question, or found the transcript unreadable for one of the fixed reasons. The limit: a session that writes the transcript itself, or runs as you with a program of its own, can forge an answer, as for holds and levels. The checks stop accidents and the obvious forms (a session running a hook by hand, starting another Claude Code session with `claude -p`, or typing into a terminal it made); they are not a boundary against a session that is trying to get round them.

A built dashboard page is never committed, copied to a branch or sent by hand: a Bash call that names `mind.html` together with `git`, `gh`, `curl`, `scp`, `rsync`, `sftp` or `wget` is denied, because that skips the privacy check of `publish.py`. `publish.py` is the only way the page leaves the machine. It checks the record's own text and the page against the privacy rules and the static guard, reads your holds, and goes on your answer; it makes the branch (one commit with no parent that holds the page and an empty `.nojekyll`) and switches GitHub Pages on only when the question you answered said so, and a private record only when it said PRIVATE. GitHub's answers are held against those flags again at the send. It reads the file back and prints a link only for an address of the expected form that serves this branch.
